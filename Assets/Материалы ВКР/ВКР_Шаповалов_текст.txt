Введение
Игровая индустрия, встраиваясь в контуры цифровой экономики, в последние годы закрепилась в числе наиболее заметных её сегментов, причём, как показывают данные аналитических источников [27, 34, 57], объём выручки данного рынка сопоставим с доходами иных крупных развлекательных отраслей и в ряде случаев превышает их. Видеоигры приобрели статус массового культурно-экономического феномена.
В структуре рынка видеоигр наряду с AAA-проектами, характеризующимися многомиллионными бюджетами и масштабной производственной кооперацией, существенную долю формирует продукция независимых разработчиков (инди-сегмент), нередко выступающая источником инновационных механик и жанровых экспериментов. В инди-сегменте устойчиво представлены roguelike-игры и RPG: для roguelike типичны процедурная генерация, высокая реиграбельность и значимость решений игрока, последствия которых, будучи накоплены в ходе прохождения, зачастую сохраняются до его завершения, тогда как RPG, фокусируясь на развитии персонажа, предполагают выбор класса, способностей, экипировки и параметрическое изменение характеристик. Совмещение указанных жанровых моделей обеспечивает одновременную вариативность игровых сессий и долгосрочную траекторию прогрессии персонажа. Практическая реализация проекта в формате 2D с видом сверху (top-down), снижая порог вхождения за счёт наглядности и читаемости сцены, при интеграции RPG и roguelike способна повысить вовлечённость пользователя. Итоговая предпосылка проста: доступность восприятия усиливает готовность игрока к повторяемым прохождениям.
Экономическая привлекательность разработки в парадигме 2D top-down детерминируется, с одной стороны, относительно низким порогом входа в части изобразительных ресурсов (в отличие от производства сложных трёхмерных моделей), а с другой – потенциальной доходностью, подтверждаемой примерами успешных проектов, демонстрирующих многолетнее удержание аудитории и стабильные продажи. При этом, хотя визуальный стиль для 2D top-down игр сохраняет значимость, определяющее влияние на восприятие продукта оказывает игровой процесс, внутри которого особую роль приобретает поведение NPC: когда противники и союзники реагируют на ситуацию убедительно и контекстно, игрок точнее воспринимает структуру сложности, дольше удерживает интерес к прохождению и в целом позитивнее оценивает игровой опыт. Жанр roguelike восходит к Rogue (1980), одной из ключевых особенностей которой являлась случайная генерация подземелий; впоследствии жанровая форма претерпела существенную эволюцию, включив, помимо классических пошаговых реализаций, динамичные проекты с элементами action-RPG. Вместе с тем в значительной части современных игр жанра поведение противников остаётся ограниченным и, как правило, редуцируется к преследованию игрока, атаке по таймеру либо следованию заранее заданным шаблонам, что приводит к доминированию простых поведенческих паттернов (фиксированные траектории движения и ограниченный набор действий). Следовательно, разработка адаптивного искусственного интеллекта (ИИ), способного анализировать процедурно сгенерированное окружение, координировать взаимодействие с другими NPC и выбирать тактику в зависимости от стиля игры пользователя, представляет собой нетривиальную научно-техническую задачу, требующую интеграции методов машинного обучения и классических подходов к проектированию интеллектуальных агентов.
В контексте рассматриваемой проблематики особое значение приобретает изменение пользовательских ожиданий: игроки всё чаще ориентируются не на заранее заданные шаблоны, а на ситуативную реакцию NPC, коррелирующую с действиями пользователя. Параллельно с этим разработка игровых ИИ-систем сохраняет прикладную востребованность, поскольку подобные решения применяются как в учебных, так и в коммерческих проектах. Тем самым создание модульной системы поведения NPC для 2D RPG обладает одновременно исследовательской и практической значимостью.
Цель настоящей работы заключается в разработке двухмерной ролевой игры с видом сверху и интеграции в неё интеллектуальной системы поведения неигровых персонажей, обеспечивающей адаптивное, тактически разнообразное и реалистичное поведение союзников и противников, а также их связи между собой. Требуется сформировать программно реализуемый контур поведения NPC, устойчивый к вариативности игровых ситуаций.
Объект исследования: программное обеспечение, реализующее 2D-игру и модели поведения неигровых персонажей.
Предмет исследования: алгоритмы и методы искусственного интеллекта (конечные автоматы, деревья поведения, машинное обучение), используемые для создания интеллектуальных агентов в динамически изменяемой игровой среде.
Для достижения поставленной цели необходимо решить следующие задачи.
Провести сравнительный анализ существующих игровых движков и фреймворков с точки зрения их пригодности для реализации сложной ИИ логики, обосновав выбор инструмента.
Разработать архитектуру игрового приложения, включающую систему управления игроком, ИИ NPC, пользовательский интерфейс, RPG реализацию.
Реализовать интеллектуальную систему поведения NPC, а именно систему принятия решений на основе конечных автоматов или деревьев поведения, и имплементировать в неё методы машинного обучения.
Провести тестирование разработанного решения, включающее функциональное тестирование ИИ логики и нагрузочное тестирование производительности при большом количестве активных NPC.
Оценить перспективы расширения игры, включая добавление нового контента и внедрения многопользовательского взаимодействия.
Подготовить документацию, провести анализ затрат и оценку безопасности труда при пользовании и разработке программного продукта.
Методологическая основа работы включает принципы объектно-ориентированного и компонентного проектирования, подходы к архитектуре игровых приложений, а также методы разработки игрового искусственного интеллекта: конечные автоматы, деревья поведения, Utility AI и обучение с подкреплением.
Структурно выпускная квалификационная работа включает введение, теоретическую часть, сравнение доступных решений, создание архитектуры приложения, практическую реализацию, раздел тестирования, анализ безопасности и экономическое обоснование проекта, список использованных источников и приложения с кодом и иллюстрациями.
В процессе подготовки работы для формулирования отдельных гипотез, реферирования источников, поиска формулировок, а также создания плана повествования, основанного на созданном продукте, применялись большие языковые модели, в частности нейросети DeepSeek, ChatGPT 5.5 и Composer 2.5. Использование данного инструментария носило вспомогательный характер: все сгенерированные тексты критически переосмысливались, проверялись и дорабатывались автором самостоятельно.

Общие принципы разработки игр
На начальном этапе создания игрового продукта приоритетной задачей выступает выбор среды разработки, поскольку игровой движок, являясь базисом технологического контура, предоставляет инструменты и библиотеки для работы с графикой, физикой, звуком, искусственным интеллектом и иными подсистемами; в качестве наиболее популярных решений, согласно [30], фиксируются Unity – кроссплатформенный движок с широким спектром возможностей и активным сообществом, Unreal Engine – высокопроизводительная платформа, ориентированная на фотореалистичную графику и передовые технологии, а также Godot Engine – свободный и открытый движок, сочетающий удобный интерфейс с поддержкой 2D и 3D разработки. Кратко: выбор движка задаёт верхнюю границу архитектурных возможностей.
Разработка игр, интегрируя программную инженерию, алгоритмы реального времени и гейм-дизайн, предъявляет к приложению требования, среди которых выделяются стабильная частота кадров, низкая задержка обработки ввода, корректность физики, графики, звука и пользовательского интерфейса, вследствие чего выбор движка и архитектуры проекта непосредственно коррелирует с качеством дальнейшей разработки, что также отмечено в [4, 20]. Следовательно, технологическая платформа в данном контексте интерпретируется не как вспомогательный инструмент, а как фактор, предопределяющий стоимость изменений и сложность сопровождения.
Для игрового проекта принципиально значима понятная и расширяемая архитектура, поскольку даже при небольшой команде структура должна обеспечивать быстрый доступ к модулям, локальную модификацию механик и добавление нового контента без радикальной переработки уже написанного кода, что снижает вероятность ошибок и упрощает сопровождение, о чём свидетельствует [32]. Резюмируя сказанное, архитектурная прозрачность выступает условием управляемого масштабирования.
В рамках разработки 2D top-down RPG критическими оказываются паттерны управления сущностями – Entity-Component-System (ECS) – а также объектно-ориентированный подход с компонентами MonoBehaviour; в [32, 50] описывается создание RPG с использованием ИИ, где архитектурное решение опирается на разделение логики поведения, данных персонажа и визуального представления. Unity, предоставляя встроенные средства анимации, физики и навигации, для top-down проектов, однако, нередко требует собственной реализации поиска пути на основе сетки тайлов, как отмечено в [11, 14]. Концептуальный анализ работ [4, 20, 50] позволяет утверждать, что наиболее жизнеспособными являются архитектуры с низкой связанностью (loose coupling) между системами генерации уровней, искусственного интеллекта NPC, боевой механикой и Пользовательским интерфейсом (UI), поскольку при такой организации изменения в одном компоненте оказывают минимальное влияние на остальные, повышая гибкость, масштабируемость и удобство обслуживания системы. Слабая связанность снижает цену эволюции проекта.
Жанр roguelike характеризуется сочетанием уникальных игровых сессий, процедурной генерации уровней и полным либо частичным сбросом прогресса посредством смерти; в [7, 11, 13] подчёркивается значимость баланса, предполагающего, с одной стороны, недопущение непроходимых испытаний, а с другой – сохранение «вызова», при этом низкая, равно как и чрезмерно высокая сложности, способны отталкивать игрока. В исследованиях [32, 35 41] акцентируется, что рогалики формируют удобный полигон для тестирования ИИ-алгоритмов благодаря высокой вариативности состояний, а в [36] предлагается применение ИИ-агентов для автоматизированного игрового тестирования, что косвенно эксплицирует трудоёмкость ручной проверки баланса.
Разработка игры выбранного жанра предполагает наличие масштабируемой архитектуры, обеспечивающей низкую связанность модулей и эффективное управление состоянием множества сущностей; при этом на практике используются объектно-ориентированные модели с наследованием, компонентно-ориентированные решения и архитектуры, основанные на сущностях и компонентах. Далее приводится теоретическое исследование указанных архитектурных вариантов.
Объектно-ориентированная архитектура с наследованием – традиционный подход, при котором игровые сущности наследуются от базового класса, поведение и данные инкапсулируются внутри классов, а специализация достигается переопределением виртуальных методов.
Преимущества: простота освоения на начальном этапе, прямое отображение модели предметной области, естественная поддержка полиморфизма.
Недостатки: ключевым ограничением становится формирование «хрупкого базового класса», когда изменения в корневой части иерархии транзитивно затрагивают всех наследников; применительно к данному проекту это критично, поскольку при росте числа типов врагов, союзников и их уникальных способностей иерархия быстро разрастается, усложняя модификацию, а повторное использование кода ведёт к дублированию либо вынужденным абстракциям, не соответствующим предметной области.
Компонентно-ориентированная архитектура (на основе MonoBehaviour) – характерная для Unity система, в которой сущность выступает контейнером для независимых компонентов, каждый из которых реализует отдельный аспект поведения и взаимодействует с другими компонентами того же объекта через прямые ссылки либо систему сообщений.
Преимущества: высокая гибкость и повторное использование компонентов, при котором поведение конструируется композиционно; новый тип врага может быть сформирован добавлением требуемых компонентов без создания нового класса-наследника, что непосредственно уменьшает проблемы масштабирования и модификации.
Недостатки: слабая структурированность данных и потенциальные риски производительности при большом числе активных сущностей; кроме того, сложное взаимодействие множества компонентов на одном объекте способно формировать неочевидные зависимости и затруднять отладку.
Архитектура Entity-Component-System – современный подход, где сущность интерпретируется как идентификатор, компоненты – как «чистые» структуры данных без логики, а системы – как функции, итеративно обрабатывающие сущности с заданными наборами компонентов.
Преимущества: высокая производительность, обусловленная организацией данных в памяти и возможностью многопоточных вычислений, а также чёткое разделение данных и поведения, упрощающее тестирование и поддержку.
Недостатки: высокий порог вхождения, потенциально увеличивающий сроки разработки; кроме того, портирование комплексных систем (анимация, навигация, UI) в ECS-стиль часто проблематично либо практически невыполнимо, вследствие чего при умеренном количестве сущностей (десятки) выигрыш производительности может не компенсировать затрат на внедрение.
Определение и роль игрового ИИ
Игровой ИИ, отличаясь от исследовательского ИИ целеполаганием, ориентирован не на нахождение оптимального решения как такового, а на формирование убедительного и интересного поведения персонажей, причём NPC не обязан действовать идеально: его действия должны оставаться понятными игроку, достаточно правдоподобными и одновременно не создавать чрезмерной вычислительной нагрузки на систему; данное положение, подмеченное в фундаментальных трудах [49, 60], является методологической основой проектирования игрового ИИ. К ключевым задачам игрового ИИ обычно относят движение, принятие решений, тактическое и стратегическое планирование и обучение, однако в [15] дополнительно отмечается применимость ИИ к процедурной генерации контента.
В монографии [60] подчёркивается, что игры формируют уникальную среду для тестирования ИИ-алгоритмов, поскольку, оставаясь сложными, они допускают повторяемые эксперименты; при этом авторы классифицируют игровой ИИ по трём направлениям: ИИ для прохождения игр, ИИ для генерации игрового контента и ИИ для моделирования поведения игроков. Данная работа также предоставляет систематическое описание обучения с подкреплением в контексте игр, что впоследствии используется при обосновании выбора гибридной архитектуры; второе издание монографии [61], обновлённое с учётом последних достижений в области глубокого обучения и больших языковых моделей, подтверждает актуальность применения ML-подходов в игровой индустрии. Исследовательская повестка смещается к адаптивным методам.
Классический труд [49] систематизирует практические методы реализации игрового ИИ, детально рассматривая алгоритмы поиска пути, управляющее поведение, конечные автоматы, деревья поведения и основанный на полезности ИИ; для настоящей работы особую ценность представляет раздел о гибридных архитектурах, в рамках которых детерминированные методы сочетаются с элементами обучения. Монография [40], фокусируясь на практической реализации «state-driven» и «goal-driven» агентов на C++, несмотря на год издания (2005), сохраняет актуальность в части фундаментальных принципов и служит базой для понимания эволюции игрового ИИ.
В [3] анализируются перспективы развития ИИ в игровой индустрии, подчёркивающие переход от жёстко заданных алгоритмов к адаптивным системам, способным подстраиваться под стиль игры конкретного пользователя; в [12] показывается, что качественный искусственный интеллект NPC позитивно влияет на пользовательский опыт, в частности на вовлечённость и реиграбельность, при этом игроки проводят больше времени в проектах с «умными» и менее предсказуемыми противниками, что особенно существенно для рогаликов, где ценность представляет каждое новое прохождение.
В [28] обобщается текущее состояние практики: доминируют деревья поведения (behavior trees – BT) и utility-based AI, тогда как нейросетевые подходы ограничены из-за непредсказуемости и вычислительных затрат; эволюция от конечных автоматов к генеративным моделям рассматривается в [31], а в [39, 40, 52, 60, 61] подтверждается, что для жанров с высокой динамикой предпочтительны детерминированные либо управляемо-случайные алгоритмы с чёткими критериями качества. Ранние реализации NPC опирались на конечные автоматы (Finite State Machines – FSM) и скриптовые последовательности, однако ключевым недостатком FSM выступает экспоненциальный рост числа состояний при усложнении поведения; последующим этапом стали иерархические конечные автоматы (Hierarchical Finite State Machines – HFSM) и деревья поведения. Современные тренды включают глубокое обучение с подкреплением (deep reinforcement learning – DRL) для обучения NPC в процедурно-генерируемых средах, но, как показывают в [58], прямое применение DRL в roguelike-играх сталкивается с проблемой разреженности награды и нестабильности обучения. Резюмируя, в прикладной разработке чаще выбираются гибридные схемы: дерево поведения как основная структура, отдельные узлы которой могут имплементировать utility-функции либо обучаемые компоненты.
Анализ методов и алгоритмов поведения NPC
Основной научной задачей выступает разработка интеллектуальной системы управления поведением NPC, способной функционировать в динамически изменяемом и процедурно генерируемом окружении, где, с одной стороны, требуется вычислительная устойчивость в условиях ограниченного бюджета времени кадра, а с другой – тактическая вариативность, обеспечивающая правдоподобие реакции на действия пользователя. Необходима модель, сочетающая управляемость и адаптивность.
Конечные автоматы и их иерархии моделируют поведение как набор дискретных состояний и правил перехода между ними, причём условия переходов, как правило, задаются булевыми выражениями, зависимыми от параметров среды и внутреннего состояния агента.
Преимущества: предельная простота реализации и интерпретации, детерминированность и предсказуемость, упрощающие отладку и обеспечивающие стабильность.
Недостатки: экспоненциальный рост сложности при расширении набора состояний и условий, ограниченная гибкость принятия решений; иерархические конечные автоматы частично нивелируют указанные ограничения за счёт введения суперсостояний и подсостояний, однако внутреннее усложнение по-прежнему сохраняется как фактор риска.
Следовательно, FSM целесообразно применять для верхнеуровневого управления общим контекстом поведения противников, однако для организации тактически разнообразного управления союзниками данный подход оказывается недостаточным.
Деревья поведения представляют собой иерархическую структуру узлов, выполняемых слева направо, где узлы подразделяются на управляющие (Sequence, Selector, Parallel) и исполняемые (Action, Condition); BT рассматриваются как индустриальный стандарт для проектов AAA-класса, что объясняется их модульностью и удобством повторного использования поддеревьев.
Преимущества: высокая масштабируемость, при которой добавление новой тактики часто сводится к включению новой ветви в узел Selector без трансформации уже существующей логики; визуальная репрезентация облегчает совместную работу программистов и гейм-дизайнеров; приоритезация действий, естественно поддерживаемая BT, выгодно отличает данный подход от FSM.
Недостатки: детерминированность, способная порождать предсказуемые реакции, а также риск деградации производительности при чрезмерной глубине дерева из‑за регулярного пересчёта состояний узлов.
В рамках рассматриваемого проекта BT представляется оптимальным выбором для тактического «скелета» NPC‑союзников и элитных врагов, определяя роль персонажа в группе и переключение между высокоуровневыми режимами.
Машинное обучение и обучение с подкреплением (ML/RL) основаны на обучении агента посредством взаимодействия со средой, где агент, получая наблюдения (вектор состояния среды), генерирует действие и оптимизирует стратегию с целью максимизации накопительной награды, формируемой через положительное подкрепление за успешные действия и отрицательное – за неудачные.
Преимущества: потенциал формирования адаптивного и менее предсказуемого поведения, обнаруживающего неочевидные для разработчика решения; способность агента реагировать на динамику окружения и стиль игры пользователя, что коррелирует с критерием высокой реиграбельности.
Недостатки: эффект «чёрного ящика», затрудняющий диагностику и обеспечение корректности поведения в краевых случаях; длительность и ресурсоёмкость обучения; феномен «катастрофического забывания», при котором агент, оптимизируя локальную награду, может утрачивать критически важные базовые тактики.
Чистое RL‑решение неприемлемо для продукта, ориентированного на стабильность и объяснимость, однако RL‑модуль обладает высокой ценностью при решении локальных подзадач, требующих гибкости.
В контексте поставленной цели целесообразно использовать гибридный подход, в котором дерево поведения задаёт общую структуру действий NPC и обеспечивает предсказуемые тактические решения (например, переход к атаке или отступлению), тогда как обучаемый RL‑компонент включается внутри отдельных боевых задач, где ручная формализация всех вариантов поведения оказывается затруднительной. В описываемой модели BT управляет глобальной тактикой NPC: принимается решение о переходе в состояние «Бой», производится оценка ситуации и активируется соответствующая ветка (например, «Дальний бой»), после чего в узле Action, вместо жёстко заданной последовательности, управление передаётся RL‑агенту.
Агент, обученный решать конкретную микрозадачу, принимает на вход локальные наблюдения (расстояние до цели, наличие стен, собственное здоровье, действия других NPC) и формирует низкоуровневые команды («стрелять», «сменить позицию на указанную точку», «ждать»), вследствие чего BT гарантирует соблюдение базовых ограничений безопасности (например, обязательность отступления при низком здоровье), а конкретная траектория манёвра во время атаки определяется адаптивной политикой. BT задаёт рамки, RL уточняет исполнение.
В [2] выполнен систематический обзор методов принятия решений игровым ИИ, где выделяются три категории: реактивные (FSM, BT), делиберативные (планирование на основе поиска) и гибридные; в [37, 38] анализируются особенности поведения NPC в виртуальных мирах и предлагается алгоритм выбора метода в зависимости от требуемой сложности и вычислительных ресурсов. Деревья поведения, детализированные в [42], закрепились как стандарт в AAA‑играх благодаря модульности и повторному использованию веток, однако в [43] фиксируются типичные ошибки проектирования BT, включая «глубокие деревья» (deep trees), дублирование логики и сложности отладки асинхронных действий; в [48] предлагается интеграция utility‑решений в BT, что позволяет динамически выбирать действие на основе взвешенных критериев. Процедурное создание деревьев поведения для NPC продемонстрировано в [44], что релевантно для roguelike‑игр с высокой вариативностью.
Нетрадиционные подходы также находят применение. В [1] предлагается построение искусственной иммунной системы для реализации ИИ в компьютерной игре, где метафора антител и клональной селекции используется для адаптации NPC к тактикам игрока; в [8] разработан шаблон поведения игрового бота на основе цепей Маркова, обеспечивающий стохастическую, но контролируемую последовательность действий; в [9, 13] исследуется сбор данных о действиях игрока для обучения NPC в шутерах от первого лица, причём методологическая часть потенциально применима и в top-down RPG. В работах [10, 16, 17] рассматривается использование нейронных сетей для моделирования поведения NPC и анализируется применение генеративно-состязательных нейронных сетей (generative adversarial network – GAN) для roguelike‑проектов, преимущественно в задачах генерации контента; одним из редких примеров успешного обучения NPC в процедурных окружениях являются глубокие политики (Deep Policy Networks), адаптирующиеся к изменяющимся параметрам дизайна, представленные в [54].
Отдельного внимания заслуживают гибридные подходы, сочетающие сильные стороны детерминированных методов и машинного обучения: FSM или BT рассматриваются как «скелет» поведения, гарантирующий выполнение ключевых тактик, а RL‑агент – как модуль, принимающий решения внутри состояний либо влияющий на переключение контекстов. Возможные варианты интеграции.
RL как замена листьев (действий) в BT. Узлы‑действия (leaf nodes) заменяются политикой, обученной с подкреплением: например, «Атаковать» вместо фиксированной последовательности вызывает RL‑агента, выбирающего выстрел, смену позиции или отступление на основе наблюдений (здоровье, расстояние, положение укрытий), что повышает гибкость в рамках заданной структуры.
RL для динамического выбора поддеревьев. Utility‑функция, определяющая активное поддерево, может быть заменена RL‑модулем, обучающимся переключать контекст (например, с «атаки» на «поиск укрытия») по критерию долгосрочной награды, вследствие чего поведение приобретает более стратегический характер.
Иерархическое RL (HRL) с уровнями абстракции. Высокоуровневая политика выбирает подзадачу (например, «занять укрытие»), а низкоуровневые политики либо классические контроллеры реализуют её, что соотносится с идеей опций (options) и естественно сочетается с иерархическими конечными автоматами.
Обобщая источники [2, 37, 38, 42, 48, 54, 58], целесообразно выделить критерии сравнения: вычислительная сложность, лёгкость отладки, способность к адаптации, поддерживаемая сложность поведения, детерминированность, возможность обучения на опыте. Для 2D top-down roguelike RPG с большим числом NPC (десятки на уровне) и требованием быстрой реакции наиболее обоснованными являются: деревья поведения – как основной каркас, utility‑оценки – для выбора тактических целей, цепи Маркова – для стохастической вариативности рутинных действий, гибридные BT+RL‑архитектуры – для боевых режимов, требующих адаптации, а также иммунные системы – в качестве экспериментального компонента долгосрочной адаптации к стилю игрока. Нейросетевые методы [16, 17, 54] без гибридного каркаса представляются избыточно сложными для данной ВКР по требованиям к обучению, данным и отладке, однако при интеграции с BT их потенциал формирования менее предсказуемого ИИ оценивается как практически реализуемый.
Анализ методов процедурной генерации контента
Процедурная генерация контента является жанрообразующим признаком roguelike, поскольку она обеспечивает вариативность уровней и, следовательно, поддерживает ключевую характеристику жанра – реиграбельность. В [29, 55] классифицируются методы PCG (Procedural Content Generation): случайная генерация, шум Перлина, BSP(binary space partitioning)-деревья, грамматики форм и эволюционные алгоритмы; при этом рассматривается и гибридный подход, сочетающий шаблоны (префабы комнат) и соединяющие коридоры, генерируемые посредством BSP, что разбирается в [45]. В исследованиях [46, 47, 56] охватывается применение глубокого обучения для PCG, включая вариационные автоэнкодеры и GAN, анализируется интеграция больших языковых моделей (large language model – LLM) в PCG, открывающая возможности генерации описаний, квестов и диалогов, а также приводятся практические рекомендации по внедрению PCG в игровой движок, включая контроль над «зерном» (seed) случайности для воспроизводимости. PCG эволюционировала от простых стохастических схем к управляемым гибридным конвейерам.
Генерация контента по текстовым подсказкам (prompt-driven), хотя и фиксируется как перспективная, в 2D top-down среде осложняется требованиями к согласованности тайловых структур, что отмечается в [51]; в [59] дополнительно поднимается проблема оценки PCG‑систем – необходимость метрик реиграбельности, разнообразия и соответствия дизайну. В [53] вводится концепция PCGBT (Procedural Content Generation using Behavior Trees), где дерево поведения управляет процессом генерации, а каждый узел отвечает за размещение определённого типа объектов, обеспечивая декларативность и повторное использование правил; экспериментальная проверка применения GAN для генерации уровней рогалика представлена в [11], причём подчёркивается необходимость постобработки результата для обеспечения проходимости.
С точки зрения обучения RL‑агентов для NPC вариативность PCG [45, 55] приобретает инструментальную значимость: процедурное разнообразие тренировочных уровней (генерация комнат, размещение врагов и укрытий) снижает риск переобучения агента под фиксированную карту. Следовательно, в рамках ВКР планируется интеграция PCG с процессом обучения, где генератор уровней используется как источник разнообразных сред для тренировки RL‑компонента; при этом наиболее реалистичным для внедрения представляется гибридный метод, включающий базовое BSP‑разбиение уровня, последующее размещение комнат‑префабов и процедурную расстановку NPC, ловушек и сокровищ на основе вероятностных правил. PCG выполняет роль «генератора распределения сред».
Критерии качества оценки интеллектуальной системы
На основе анализа литературы [36, 37, 38, 59, 60] и специфики жанра формулируются критерии качества, применимые для оценки разрабатываемого решения.
Вычислительная эффективность – время обработки ИИ на одного NPC не должно превышать 0.5 мс на среднем оборудовании [15, 52].
Адаптивность – способность NPC изменять тактику в ответ на действия игрока [2, 48].
Разнообразие поведения – количество различимых паттернов действий NPC за сессию, измеряется через логгирование [37, 38].
Детерминированность и случайность – баланс: поведение не должно быть полностью предсказуемым, но и не должно выглядеть хаотичным. Коэффициент стохастичности должен настраиваться [8, 42].
Простота отладки и модификации – архитектура должна позволять изменять параметры поведения без перекомпиляции всего проекта (например, через ScriptableObject в Unity) [43, 50].
Интегрируемость с PCG – ИИ должен корректно работать на любом процедурно сгенерированном уровне без ручной настройки навигационных сеток [45, 53].
Обучаемость (для RL-компонента) – способность агента улучшать свои показатели (например, эффективность в бою) в процессе тренировки; измеряется ростом суммарной награды за эпизод [54, 58].
Перечисленные критерии используются во второй главе при сравнении предложенной гибридной архитектуры (BT + RL) с базовыми решениями (конечный автомат и простое дерево поведения). Оценка строится на сочетании производительности, управляемости и качества поведения.
Выводы по главе
Анализ источников демонстрирует, что деревья поведения сохраняют статус одного из наиболее удобных инструментов проектирования NPC, поскольку позволяют декомпозировать поведение на независимые ветви и упрощают отладку; Utility AI, в свою очередь, целесообразно применять для выбора действий на основе текущего состояния игровой ситуации, тогда как обучение с подкреплением оказывается оправданным в тех фрагментах поведения, где исчерпывающее ручное описание вариантов затруднено. Для разрабатываемой игры наиболее обоснован гибридный подход.
Наряду с этим выявляются ограничения. Классические конечные автоматы быстро теряют сопровождаемость при росте числа состояний; чисто стохастические методы, включая цепи Маркова без контекстной «надстройки», способны генерировать несогласованное поведение, снижающее эффект погружения; нейросетевые подходы в чистом виде предъявляют повышенные требования к вычислительным ресурсам и длительности обучения, не обеспечивая при этом гарантированной предсказуемости. При использовании обучения с подкреплением вне классического каркаса систематически проявляется риск «забывания» критически важных тактик (например, отступления) в пользу локально выгодных, но стратегически убыточных действий.
В качестве направления модернизации определяется необходимость разработки гибридной архитектуры поведения NPC, объединяющей дерево поведения как верхний уровень принятия решений с RL‑компонентом, обученным в среде Unity ML-Agents, а также Utility AI для выбора конкретных действий в боевых режимах; дерево поведения должно обеспечивать глобальные тактические переключения, RL‑агент – исполнение манёвров, Utility AI – выбор цели атаки. Предлагается формировать конфигурируемые профили поведения для различных типов NPC с возможностью оперативной настройки через инспектор Unity с использованием ScriptableObject, что снижает издержки масштабирования; дополнительно требуется методика оценки по сформулированным критериям, включающая автоматизированное тестирование с логгированием действий и ручную экспертную оценку, а для RL‑компонента – оценку сходимости обучения и способности к генерализации на новых процедурно-сгенерируемых уровнях.
Первая глава подтверждает актуальность разработки интеллектуальной системы поведения NPC для 2D top-down roguelike RPG, причём выявленные недостатки классических методов и практические риски чистого RL концептуально обосновывают выбор гибридной архитектуры (BT + RL) с использованием фреймворка Unity ML-Agents. Предметом второй главы становится формализация выбранной архитектуры и её теоретическое обоснование.
Теоретическое исследование и разработка архитектуры интеллектуальной системы поведения NPC
Данная глава ориентирована на теоретическое исследование и синтез методов, необходимых для построения комплексной системы поведения неигровых персонажей в рамках двухмерной ролевой игры с видом сверху, при этом, опираясь на выводы первой главы, где были зафиксированы ограничения классических подходов и потенциал гибридных решений, далее выполняется сравнительный анализ инструментальных средств, формальных моделей представления поведения и структурных решений, формирующих архитектуру программного продукта. Цель главы – зафиксировать теоретическую основу выбранной архитектуры.
Ключевой задачей выступает разработка подхода, сочетающего детерминированное управление и обучаемые компоненты для достижения адаптивного, тактически разнообразного и вычислительно эффективного поведения NPC в условиях процедурно генерируемого окружения. Результатом должен стать формализуемый метод, пригодный для практической реализации.
	Выбор инструментальных средств разработки игры
Выбор игрового движка, будучи первичным архитектурным решением, задаёт ограничения по структуре проекта и определяет доступный инструментарий реализации как геймплейных механик, так и интеллектуальных подсистем; следовательно, в контексте разработки 2D игры с видом сверху и элементами рогалика движки целесообразно оценивать по совокупности критериев, напрямую связанных с целевыми требованиями к производительности, навигации и поддержке ИИ. Движок выбирается не по популярности, а по совокупности ограничений.
Критерии выбора включают.
Производительность 2D рендеринга – эффективность работы с тайловыми картами, спрайтовыми атласами, системой частиц, 2D анимацией.
Возможности навигации и поиска пути – наличие встроенных или легко интегрируемых решений для навигации по тайловой сетке, включая динамическое перестроение путей.
Поддержка инструментов ИИ – наличие фреймворков для реализации, деревьев поведения, а также машинного обучения.
Экосистема и расширяемость – доступность готовых ассетов, качество документации, простота масштабирования проекта.
Лицензионная политика – ограничения бесплатных версий, роялти.

Выбор Unity обосновывается следующим набором аргументов, отражающих связь платформенных возможностей с целями ВКР.
Наличие ML-Agents – данный фреймворк обеспечивает наиболее бесшовную на сегодняшний день интеграцию обучения с подкреплением в игровой движок, позволяя обучать нейросетевые политики непосредственно в среде выполнения игры.

Резюмируя сказанное, Unity выделяется как платформа, предлагающая компромисс между функциональностью 2D-инструментария, глубиной поддержки ИИ-разработки и зрелостью экосистемы, что критически значимо для проекта, в котором ядро формируется гибридной интеллектуальной системой.
Выбор моделей поведения NPC
На основании выводов первой главы для разрабатываемого проекта сформулированы требования к моделям поведения союзников и противников, причём различие ролей NPC приводит к асимметрии требований по вычислительной стоимости, объяснимости и степени адаптивности. Единая модель для всех NPC не является оптимальной.
Союзники в одиночном режиме, фактически компенсируя отсутствие других игроков, используют тот же игровой стек, что и персонаж игрока: PlayerStats, EquipmentComponent, AbilitySystem, ActiveWeapon; от союзников требуется координация с лидером, осмысленный выбор целей и способностей, а также адаптивное боевое позиционирование с учётом типа оружия и входящих угроз (ближний бой, снаряды дальнобойных врагов), при этом допускается повышенная вычислительная стоимость на одного агента. Следовательно, для союзников допустим более сложный контур принятия решений.
Противники (слайм, голем и темный маг), напротив, представлены массовыми однотипными юнитами, где приоритетными становятся детерминированность, предсказуемость для геймдизайна и экономичность по CPU; достаточным набором функций выступают преследование, атака, отступление и реакция на урон. Итоговая предпосылка проста: массовый враг должен быть «дешёвым» и управляемым.
В таблице 2.2 представлено сопоставление методов ИИ по ролям NPC. Ключевое теоретическое решение, рассматриваемое как элемент научной новизны: обучение с подкреплением не применяется end-to-end для всего поведения бота, поскольку задача декомпозируется на подзадачи с разделением ответственности – Unity Behavior определяет контекст (когда искать врага, атаковать, применять способность, включать ML-управление движением), Utility AI (WeaponTargetSelector, UtilityAbilitySelector) отвечает за выбор цели и способности, ML-Agents (политика AllyPosition) реализует боевое позиционирование (дистанция, стрейф, отступление), а AllyMLMovementModifier + AllyDodgeHeuristic исполняют движение на NavMesh. RL ограничивается микрозадачей, а «каркас» остаётся классическим.

Ключевое теоретическое решение, составляющее элемент научной новизны работы: обучение с подкреплением не применяется end-to-end для всего поведения бота. Задача декомпозируется на подзадачи с разделением ответственности: Unity Behavior – когда искать врага, атаковать, применять способность, включать ML-управление движением; Utility AI (WeaponTargetSelector, UtilityAbilitySelector) – кого атаковать и какую способность использовать; ML-Agents (политика AllyPosition) – как держать боевую дистанцию, стрейфить и отступать; AllyMLMovementModifier + AllyDodgeHeuristic – исполнение движения на NavMesh.
Данный подход коррелирует с рекомендациями гибридных архитектур [49, 60, 61], согласно которым классический контур гарантирует выполнение базовых тактик (например, отступление при низком здоровье, следование за лидером), тогда как RL обеспечивает гибкость внутри активированного боевого контекста; дополнительно декомпозиция снижает размерность пространства действий – от потенциально десятков дискретных команд к четырём непрерывным параметрам позиционирования, вследствие чего упрощается конструирование вознаграждения и ускоряется сходимость обучения. Итог: сложность переносится из «всего поведения» в локальную задачу движения.
Политика AllyPosition формализуется как марковский процесс принятия решений, пространство наблюдений политики приведено в таблице 2.3, метод передачи наблюдений представлен в листинге 2.1; пространство действий включает оптимальную дистанцию, принудительное отступление при низком здоровье, направление и интенсивность стрейфов.
Центральным элементом системы управления союзниками является компонент AllyAIBrain – хаб принятия решений, вызываемый из пользовательских узлов Unity Behavior, при этом каждые 0,2 секунды обновляется «снимок» боя, формируется список атакующих врагов в радиусе ближнего боя и входящих снарядов, а полученные данные используются RL-компонентом для назначения награды при успешном избегании атак и наказания при получении урона и смерти; детальная методика будет разобрана в третьей главе. RL получает входы, релевантные угрозам, а не «сырую» сцену.

public override void CollectObservations(VectorSensor sensor)
{
    CombatSnapshot snapshot = _brain != null ? _brain.Snapshot : default;
    ThreatSnapshot threat = _threatPerception != null
        ? _threatPerception.BuildSnapshot(transform.position, snapshot)
        : default;
    sensor.AddObservation(_brain != null ? _brain.HealthPercent : 1f);
    sensor.AddObservation(_brain != null ? _brain.ManaPercent : 1f);
    sensor.AddObservation(GetShieldPercent());
    sensor.AddObservation(NormalizeCount(snapshot.EnemyCount, 8));
    sensor.AddObservation(NormalizeDistance(snapshot.NearestEnemyDistance, 12f));
    sensor.AddObservation(NormalizeCount(snapshot.ClusteredEnemyCount, 6));
    sensor.AddObservation(snapshot.AnyAllyLowHealth ? 1f : 0f);
    sensor.AddObservation(snapshot.AnyEnemyInCombat ? 1f : 0f);
    sensor.AddObservation(GetLeaderDistanceNormalized());
    sensor.AddObservation(_brain != null ? _brain.AttackDistance / 12f : 0.1f);
    sensor.AddObservation(GetProfileObservation());
    sensor.AddObservation(GetWeaponTypeObservation());
    sensor.AddObservation(NormalizeCount(threat.AttackingSelfCount, 4));
    sensor.AddObservation(NormalizeCount(threat.AttackingEnemyCount, 8));
    sensor.AddObservation(threat.IncomingThreatUrgency);
    sensor.AddObservation(NormalizeSigned(threat.ThreatDirection.x));
    sensor.AddObservation(NormalizeSigned(threat.ThreatDirection.y));
}

Выбор цели реализуется как система очков: враг получает бонусы за близость (с поправкой на тип оружия), низкое здоровье, участие в бою, фокус-атаку всей группы, а также, если он атакует самого персонажа, после чего выбирается цель с максимальным весом. Выбор способности организуется аналогично: для каждой способности вычисляются очки полезности в зависимости от типа (одиночная, групповая, лечение, защита, поддержка), доступной маны, дистанции и текущей ситуации, при этом применение разрешается только при превышении минимального порога (MinScoreToCast). Итоговый вывод короток: дискретные решения остаются объяснимыми и настраиваемыми.
	Формализация разрабатываемой архитектуры
В качестве архитектурного решения для данной работы выбрана гибридная архитектура, основанная на компонентно-ориентированном подходе с выделением систем «чистой» логики, поскольку подобная организация, избегая глубокого наследования, сохраняет гибкость композиции и одновременно упрощает интеграцию нескольких подсистем искусственного интеллекта. Архитектура должна выдерживать усложнение ИИ без деградации сопровождаемости.
Структура выделяет следующие слои.
Слой данных (Data Layer): представлен объектами ScriptableObject и легковесными структурами данных; здесь фиксируются неизменяемые конфигурации и данные времени выполнения, сериализуемые для сохранения прогресса.
Слой основных систем (Core Systems): набор чистых C# классов, не зависящих от фреймворка Unity; сюда выносится ключевая механика (расчет характеристик, логика применения способностей, процедурная генерация уровней), что повышает модульность и тестируемость и соответствует принципу слабой связанности.
Геймплейный слой (Gameplay Layer): MonoBehaviour-компоненты, связывающие чистые системы с визуальным представлением и событиями жизненного цикла Unity; сущность персонажа трактуется как корневой контейнер компонентов снаряжения, характеристик и контроллера поведения, а взаимодействие унифицируется через интерфейс, позволяющий врагам обрабатывать цели без ссылок на конкретные классы игрока или бота.
Пользовательский интерфейс (UI Layer): слой представления, подписывающийся на события геймплейного слоя и отображающий изменения состояний, не реализуя логику принятия решений.
Вынос ключевой логики в чистые C# классы устраняет перегруженность MonoBehaviour и формирует основу для интеграции сложных ИИ‑модулей, которым требуется быстрый доступ к игровому состоянию без избыточных зависимостей. Итог: управляемость системы достигается за счёт разделения ответственности.
Анализ требований фиксирует принципиальное различие между ИИ союзников и противников: союзники должны демонстрировать адаптивное, тактически осмысленное и групповое поведение, непредсказуемое в деталях, но предсказуемое на уровне стратегии, тогда как противники, будучи массовыми, могут использовать детерминированные и вычислительно дешёвые модели. На этой основе формулируется дифференцированный подход к управлению: управление союзниками – гибридная архитектура на основе деревьев поведения с интегрированным RL-компонентом; управление противниками – архитектура на основе иерархического конечного автомата с элементами Utility-оценок. Разным ролям – разные модели.
Архитектура управления союзниками включает тактический и исполнительный уровни: Unity Behavior задаёт контекст (поиск врага, бой, применение способностей), анализируя ситуацию и активируя соответствующее поддерево, что обеспечивает объяснимое переключение глобальных тактик, тогда как внутри боевого контекста ML‑политика AllyPosition управляет дистанцией и стрейфом, а AllyMLMovementModifier исполняет движение на NavMesh, обеспечивая реализацию выбранной тактики; граф поведения союзников представлен на рисунке 2.1. Для управления противниками применяется иерархический конечный автомат, где базовый уровень включает состояния блуждания, бездействия, боя и смерти, а суперсостояние бой декомпозируется на преследование, отступление и атаки; переходы управляются Utility‑функциями, оценивающими расстояние до цели, уровень здоровья и перезарядки способностей, что придаёт ограниченную вариативность без усложнения до полноценного BT, а схема HFSM противников представлена на рисунке 2.2. В листинге 2.2 приведён обработчик смены состояний противников. Итоговый тезис краток: асимметрия снижает стоимость ИИ для массовых юнитов.

Листинг 2.2 – Метод обработки состояний противников.
private void CheckCurrentState()
{
    if (!_enemyDamage.IsAlive)
    {
        TransitionTo(State.Death);
        return;
    }
    bool canAttack = Time.time > _nextAttackTime;
    State newState = State.Roaming;
    if (_state == State.Idle) newState = State.Idle;
    if (HasLiveTarget())
    {
        float dist = DistanceToTarget();
        if (_isChasingEnemy)
        {
            if (_enemyDamage.InCombat) newState = State.Chasing;
            else if (dist <= _chasingDistance)
            {
                newState = State.Chasing;
                _enemyDamage.SetCombat(true);
            }
        }
        if (_isAttackingEnemy && dist <= _attackDistance)
            newState = State.Attacking;
        if (_retreatAfterAttack && !canAttack && dist < _minSafeDistance && !IsAttacking)
            newState = State.Retreating;
    }
    if (newState != _state) TransitionTo(newState);
}
Предложенный подход включает элементы научной новизны: асимметричная ИИ‑архитектура (мощный, но дорогой интеллект для союзников при сохранении быстрого и контролируемого HFSM для массовых врагов) и контекстное RL‑исполнение (обучаемые компоненты решают строго локальные микрозадачи, активируемые древом поведения). Тем самым достигается баланс между адаптивностью и контролем.
Для функциональной декомпозиции системы управления поведением NPC применяется нотация IDEF0 (Integration Definition for Function Modeling), представляющая систему как совокупность взаимосвязанных функций с явным указанием входов (I), выходов (O), управляющих воздействий (C) и механизмов (M), что соответствует требованиям к теоретическому разделу выпускной квалификационной работы. На контекстной диаграмме, изображенной на рисунке 2.3, представлена функция управления поведением неигровых персонажей: входами выступают состояние игрового мира, ввод игрока и конфигурация профилей поведения (ScriptableObject), выходами – действия NPC (движение, атака, применение способностей) и события боя (получение урона, смерть, уничтожение врага), управление реализуется правилами Utility AI, параметрами обучения ML‑политики, графом Unity Behavior и балансом оружия и способностей, а механизмами являются Unity 6, ML-Agents, NavMesh Plus и Unity Behavior. IDEF0 фиксирует границы ответственности подсистем.

Указанная последовательность методологически значима, поскольку интеллектуальная система проектируется как часть целостного приложения, где союзник обязан действовать в рамках тех же ограничений и правил, что и персонаж игрока, используя общие механики характеристик, оружия и способностей; следовательно, проверка поведения осуществляется в условиях, приближенных к реальному игровому процессу, а не в искусственно упрощённой среде.

Практическая эксплуатация проекта реализуется в двух средах. Первая предназначена для обычной игры: пользователь управляет лидером группы, подбирает экипировку, вступает в бой с противниками и получает добычу. Вторая среда – тренировочная сцена ML_Training_Arena, в которой тот же префаб союзника используется в режимах эвристики, обучения либо применения готовой ONNX‑модели; при этом принципиальным является использование единого префаба как в игровом, так и в тренировочном контуре, поскольку данное решение снижает риск расхождения между поведением, сформированным в процессе обучения, и поведением, наблюдаемым в боевых ситуациях игрового процесса. Обучение и игра синхронизированы на уровне артефактов.
Реализация базовых игровых систем
До интеграции интеллектуального поведения NPC была сформирована базовая функциональная основа игрового приложения, включающая управление игроком, боевую систему, способности, инвентарь, экипировку, противников, систему группы и навигацию; указанные модули не рассматриваются как самостоятельная научная новизна работы, однако они создают реалистичный контекст, в котором корректность поведения союзника поддаётся проверке при соблюдении ограничений «настоящего» боя. Без полноценного геймплейного контекста валидность ИИ‑эксперимента снижается.
Управление игроком реализовано через Unity Input System: персонаж перемещается в двумерном пространстве, применяет оружие и способности, а камера сопровождает его с видом сверху. Боевая подсистема поддерживает несколько типов оружия (меч, лук, посох, талисман), для каждого из которых задаются дальность и оптимальная дистанция применения; данные параметры используются не только в пользовательском управлении, но и в логике позиционирования союзника, что обеспечивает единство правил и сопоставимость результатов.
Система способностей базируется на конфигурационных объектах AbilitySO: реализованы атакующие, защитные и поддерживающие действия (огненный снаряд, лечение, наложение щита, создание области с периодическим уроном). Компонент AbilitySystem, управляя четырьмя слотами способностей, проверяет возможность применения, учитывает ману и перезарядку, создаёт конкретную реализацию способности через AbilityFactory и уведомляет интерфейс о применении либо замене; тем самым одна и та же подсистема применяется и для игрока, и для союзника, вследствие чего бот не «имитирует» способность отдельным скриптом, а инициирует её через общий механизм. Итог краток: союзник действует в рамках тех же правил, что и пользователь.
Система характеристик и экипировки связывает инвентарь с параметрами персонажа: EquipmentComponent получает предметы, экипированные конкретным членом отряда, и формирует модификаторы характеристик, что позволяет союзнику иметь индивидуальное снаряжение и параметры, производные от общей RPG‑системы; в перспективе данная организация создаёт предпосылку для тестирования и обучения NPC различных классов без переписывания логики ИИ. Вариативность билдов поддержана архитектурно.
Менеджер группы PartyManager регистрирует живых участников группы, определяет лидера и предоставляет противникам унифицированный механизм выбора цели: для врага игрок и союзник выступают равноправными боевыми сущностями, и цель выбирается как ближайшая живая сущность из списка группы. Данное решение повышает строгость тестирования: при ошибочном позиционировании союзник получает урон, способен погибнуть и, соответственно, ухудшить итоговую награду эпизода, что делает экспериментальную среду ближе к игровым условиям.
Пользовательский интерфейс включает инвентарь, описание предметов, экипировку членов группы и панель способностей. На рисунке 3.1 представлен пользовательский интерфейс с открытой вкладкой инвентаря.


Рис. 3.1 – Внутриигровой интерфейс

ИИ противников реализован посредством конечного автомата: противник может находиться в состояниях ожидания, блуждания, преследования, атаки, отступления и смерти, а переходы определяются дистанцией до цели, признаком нахождения в бою, возможностью атаки и параметрами конкретного врага. В проект введены различные типы противников, включая ближних бойцов и дальнобойных магов; последние представляют особую значимость для исследования, поскольку их снаряды формируют динамическую угрозу, на которую союзник должен реагировать при позиционировании и уклонении. Резюмируя, базовые системы формируют среду, в которой интеллектуальная подсистема получает содержательно значимые стимулы.
На рисунке 3.2 представлен кадр из игровой сессии, на котором происходит столкновение группы игрока с противниками.


Рис. 3.2 – Демонстрация боя
Реализация интеллектуальной системы союзника
Интеллектуальная система союзника имплементирована как гибридная архитектура, в рамках которой сквозное нейросетевое управление всеми действиями не применяется, поскольку выбор цели, выбор способности и выполнение атаки обладают дискретной структурой и в значительной степени поддаются формализации через правила полезности; машинное обучение используется в той компоненте поведения, где ручная настройка становится менее надёжной, – в боевом позиционировании, выборе дистанции, стрейфе и отступлении под давлением угроз. ML применяется там, где правила быстро деградируют.
Центральным элементом выступает AllyAIBrain (приложение А), выполняющий функцию хаба принятия решений и инкапсулирующий взаимодействие с подсистемами: компонент хранит актуальный снимок боя, вычисляет долю здоровья и маны, определяет боевую дистанцию с учётом оружия, профиля поведения и параметров ML‑модели, инициирует выбор цели и выбор способности. Благодаря такой организации граф поведения взаимодействует не с множеством низкоуровневых компонентов, а с единой согласованной точкой принятия решений, что уменьшает связанность и повышает воспроизводимость поведения при изменении окружения.
Подсистема восприятия реализована через CombatPerception (приложение Б), формирующую CombatSnapshot – структурированное представление боевой ситуации, включающее позицию союзника, доли здоровья и маны, тип и дальность оружия, список врагов в радиусе сканирования, список союзников, количество противников, число сгруппированных врагов, признак раненого союзника, дистанцию до ближайшего врага и информацию о том, атакует ли противник. Для поиска врагов используется буфер Collider2D, что снижает число временных выделений памяти при регулярном сканировании и повышает предсказуемость производительности.
Дополнительно реализована подсистема ThreatPerception (приложение В), связанная с реестром EnemyProjectileRegistry: вражеские снаряды регистрируются в общем списке, после чего союзник оценивает направление угрозы, расстояние и срочность реакции, вследствие чего наблюдения ML‑агента дополняются признаками текущих атак, а не только сведениями о врагах как объектах сцены. Модель получает информацию о «процессе атаки», а не только о её источнике.
Выбор цели оружия организован через Utility AI: компонент WeaponTargetSelector присваивает каждому врагу оценку, учитывающую дистанцию до цели, оптимальную дальность текущего оружия, низкое здоровье врага, его участие в бою, количество союзников, уже сфокусированных на цели, а также факт атаки самого бота; результатом становится способность союзника добивать ослабленных противников, реагировать на непосредственную угрозу и участвовать в фокусировке урона группы. Логика выбора остаётся объяснимой и поддаётся настройке, поскольку весовые коэффициенты анализируются и корректируются через инспектор, что отражено на рисунке 3.3.


Рис. 3.3 – Настройка весов выбора цели атаки
Выбор способности реализован аналогично через UtilityAbilitySelector: для каждого слота проверяется наличие способности, возможность применения, доступная мана, дальность, тип цели и соответствие текущей ситуации, при этом лечебная способность получает повышенный приоритет при наличии раненого союзника, защитная – при росте плотности угроз, а способность по площади – при скоплении противников; если итоговая оценка не превышает минимальный порог, применение отменяется, что предотвращает расход ресурсов в ситуациях, не приносящих тактической пользы. Итог краток: дискретные решения описываются полезностью, а непрерывные – обучаемой политикой.
Оркестрация действий реализована через Unity Behavior: граф поведения задаёт порядок и параллельность (выбор врага, синхронизация переменных, атака, применение способности, перемещение), причём в боевом режиме атака, применение способности и движение допускаются параллельно, что обеспечивает правдоподобие и исключает искусственные «паузы» на принятие решения. Для интеграции ML‑позиционирования реализован пользовательский узел AllyMLCombatMovementAction, передающий управление компоненту AllyMLMovementModifier (приложение Г).
В процессе отладки выявлен конфликт навигационных команд: одновременная активность обычного движения к цели, отступления и ML‑позиционирования приводит к противоречивым назначениям для NavMeshAgent, что визуально проявляется дрожанием на границе дистанции (попеременное приближение и отход). Итоговая архитектура устраняет проблему посредством единого контура боевого движения: при активном ML‑контроле узлы классической навигации и отступления не вмешиваются в назначение точки перемещения, а боевая ветвь графа (рисунок 3.4) передаёт управление движением ML‑модулю полностью. Источник команд движения должен быть единственным.

Рис. 3.4 – Боевая ветка союзников

Таким образом, реализованная интеллектуальная система разделяет ответственность по уровням: Unity Behavior отвечает за порядок действий, Utility AI – за выбор цели и способности, ML-Agents – за параметры боевого позиционирования, а модификатор движения исполняет решения на NavMesh. Итоговый эффект двояк: поведение остаётся управляемым за счёт правил, сохраняя при этом адаптивность в микрозадаче движения.
Реализация ML-системы позиционирования
Обучаемым компонентом системы является AllyPositionAgent (приложение Д), размещённый на префабе союзника: агент, имея имя поведения AllyPosition, оперирует 17 векторными наблюдениями и 4 непрерывными действиями, причём принципиальным конструктивным ограничением выступает отказ от прямого управления персонажем через координаты, скорость либо команды атаки – модель генерирует интерпретируемые параметры, далее транслируемые в стандартные игровые механизмы движения. Нейросеть не «рулит» персонажем напрямую, а задаёт параметры поведения.
Исполнение решений возложено на AllyMLMovementModifier, переключающийся между тремя режимами – боевое позиционирование, отход к союзникам при низком здоровье и догон лидера при чрезмерном отдалении от группы, – вследствие чего обеспечивается как автономность микрозадачи позиционирования, так и соблюдение глобальных ограничений (не терять связь с группой и не игнорировать критические состояния). В режиме боевого позиционирования модуль строит целевую точку на кольце вокруг текущей цели с учётом дистанции атаки, добавляет боковое смещение, определяемое действиями модели, и валидирует точку через NavMesh.SamplePosition; если союзник оказывается слишком близко к врагу, траектория смещается в сторону отхода, а при избыточной дистанции – к расчётной позиции на предпочтительном радиусе.
Режим низкого здоровья реализован с гистерезисом: вход в отступление инициируется при снижении здоровья до порогового значения (например, 20%), тогда как возврат к боевому позиционированию разрешается только после восстановления до более высокого уровня (например, 50%), что предотвращает частое переключение режимов при колебаниях около границы и стабилизирует динамику управления. В режиме отступления союзник стремится к лидеру либо ближайшему члену группы, однако при наличии врага в непосредственной близости выполняет кратковременный шаг от источника угрозы, оставаясь в пределах группы, – данная оговорка уменьшает вероятность «запирания» агента между целями и препятствиями.
Третий режим предназначен для следования за лидером: при превышении допустимой дистанции до группы модификатор назначает точку сближения, тем самым ограничивая возможность «увода» союзника обученной политикой в ситуации, когда локально выгодное позиционирование относительно цели конфликтует с игровой задачей сопровождения. Локальная оптимизация не должна разрушать групповую когерентность.
Поверх ML‑политики функционирует реактивный эвристический слой уклонения AllyDodgeHeuristic, введённый по причине дискретности запроса решений: поскольку DecisionRequester опрашивает модель не в каждом физическом кадре, а с периодом в 5 шагов, формируется временной интервал, в котором быстро движущаяся угроза (снаряд) может потребовать немедленной реакции; эвристика, используя ThreatSnapshot, добавляет короткое смещение в безопасном направлении, если срочность угрозы превышает порог. ML обеспечивает стратегию, эвристика – мгновенную реакцию.
Функция вознаграждения AllyPositionAgent комбинирует пошаговые и событийные элементы: за удержание дистанции около предпочитаемой начисляется положительная награда; при отсутствии врагов и чрезмерном отдалении от лидера назначается штраф; событийные компоненты связываются с получением урона, поглощением урона щитом, уничтожением врага, смертью агента и успешной зачисткой волны. Дополнительно реализовано поощрение за отсутствие урона в момент атаки врага и за уклонение в ситуации, когда угроза проходит рядом без нанесения повреждения, вследствие чего политика не стимулируется к тривиальному бегству из боя, а оптимизирует компромисс между выживанием, удержанием дистанции и участием в уничтожении противников. Итог краток: награда формирует баланс, а не единственную доминанту.
В проекте предусмотрены четыре режима работы ML‑подсистемы: Disabled отключает влияние ML‑параметров, Heuristic формирует действия вручную и используется для верификации среды без обученной модели, Training активируется при подключении Python‑тренера ML-Agents, Inference применяет экспортированную ONNX‑модель в игровом процессе. Данная градация упрощает диагностику: одна и та же сцена последовательно проверяется эвристикой, обучением и инференсом.
Организация обучения, исследование гиперпараметров, проведение тестирования и отладки
Для обучения создана отдельная сцена ML_Training_Arena, включающая контроллер эпизодов AllyTrainingEnvironment, точки появления союзника, лидера и противников, генератор волн AllyTrainingEnemySpawner, запечённую NavMesh‑сетку и вспомогательный объект, имитирующий лидера группы; длительность эпизода ограничена 90 секундами, завершение фиксируется как успешное при уничтожении всех врагов и как неуспешное – при смерти агента либо истечении времени. Эпизодная постановка обеспечивает сопоставимость прогона.
Сложность среды повышается постепенно: на ранних этапах агент сталкивается с упрощённой волной, после чего состав и численность противников усложняются, доводя проверку до смешанной волны из двух ближних противников и трёх дальнобойных; необходимость учебной программы обусловлена тем, что при немедленном запуске максимально сложного сценария агент получает чрезмерно плотные штрафы и хуже усваивает базовое позиционирование, тогда как постепенное усложнение позволяет сначала сформировать устойчивый навык выживания и удержания дистанции, а затем адаптировать его к композиции разнотипных угроз. Обучение выполнялось алгоритмом PPO, итоговая конфигурация успешного прогона приведена в таблице 3.2.

Несколько первых попыток обучения использовались преимущественно для верификации размерности наблюдений и действий, устойчивости связи Unity с Python‑тренером и выявления дефектов, проявляющихся на длинных прогонах: были обнаружены ошибки сброса текущего оружия при перезагрузке эпизода либо после смерти болванки игрока, что приводило к исчезновению возможности атаки и, как следствие, к серийным неудачным эпизодам; помимо этого выявлялась некорректность завершения перезарядки базовой атаки при окончании времени эпизода вследствие структуры графа, а также дефект усложнения волн, при котором независимо от уровня сложности появлялся только один враг, лишая агента опыта взаимодействия с группой противников. Стабильность среды оказалась предварительным условием корректного обучения.
После устранения указанных проблем центральной задачей стала корректировка функции вознаграждения: при наличии штрафа времени на каждом шагу агент стремился как можно быстрее завершить эпизод путём «размена» атаками, инициируя прямое сближение и получая урон, что противоречит целевой игровой интенции; оптимальным решением выступило удаление штрафа за время эпизода при одновременном усилении штрафов за получение урона и смерть, поскольку в ходе игрового процесса приоритетом является сохранение здоровья и устойчивость поведения на протяжении забега, а не максимизация урона за минимальный интервал.
Успешным признан прогон ally_headless_v1, выполненный в сборке без графического вывода, что уменьшило накладные расходы редактора и повысило стабильность обучения на полном цикле; исследование гиперпараметров носило итерационный характер, причём наибольшее влияние оказала не отдельная локальная настройка коэффициента, а совокупность решений: введение стрейфа в пространство действий, включение признаков входящих угроз в наблюдения, нормализация входов, применение учебной программы и уточнение схемы вознаграждения. Слишком слабая награда за дистанцию не формировала устойчивого позиционирования, тогда как чрезмерный штраф за урон делал обучение чувствительным к единичным ошибкам; итоговая постановка интерпретируется как компромисс, в рамках которого агенту выгодно избегать урона, сохраняя боевую дистанцию и участвуя в зачистке волны. Обучение стабилизировалось после согласования «цены ошибок» и «цены дистанции».
На рисунке 3.5 представлен график TensorBoard, на котором отражен рост средней совокупной награды. Как мы можем заметить, агент сформировал устойчивую политику уже примерно на 600 000 шаге и дальше только улучшал ее, что видно по не сглаженному графику, представленному серым полупрозрачным цветом, на котором примерно до 800 000 шага наблюдаются резкие скачки награды, после этого значения график становится более спокойным.

Выводы по главе
В третьей главе рассмотрена практическая реализация игрового программного продукта «Dungeon Seeker» и интеллектуальной системы поведения NPC: сформирован игровой фундамент (управление персонажем, оружие, способности, враги, инвентарь, экипировка, система группы и навигация), после чего реализована гибридная архитектура поведения союзника, где Unity Behavior выполняет оркестрацию действий, Utility AI отвечает за выбор цели атаки и способности, а ML-Agents обеспечивает боевое позиционирование. Реализован многоуровневый контур принятия решений.
Разработан ML‑контур AllyPosition с 17 наблюдениями и 4 непрерывными действиями, причём модель управляет не всем поведением NPC, а интерпретируемыми параметрами движения (дистанция, отступление, направление и интенсивность стрейфа); исполнение решений реализовано через AllyMLMovementModifier с режимами боевого позиционирования, отхода к союзникам и следования за лидером, дополнительно введены гистерезис низкого здоровья и реактивное уклонение от входящих угроз. Создана тренировочная сцена ML_Training_Arena, реализованы сброс эпизодов, генерация волн и схема вознаграждения, выполнено несколько попыток обучения, включая ранние отладочные прогоны и успешный ally_headless_v1 до 1 000 054 шагов с экспортом ONNX‑модели.
Экспериментальное сравнение эвристического и обученного режимов на 30 эпизодах максимальной сложности показало преимущество обученной политики по устойчивости результата: успешность завершения выросла с 90 % до 100 %, средняя награда по всем попыткам – с 4,01 до 5,49, стандартное отклонение – снизилось с 5,34 до 1,28. Итог краток: интеграция ML‑компонента повысила предсказуемость поведения союзника в сложной боевой конфигурации.
Жизненный цикл системы
Анализ опасных и вредных производственных факторов при работе с серверным оборудованием
Одним из перспективных направлений развития разрабатываемого программного продукта является внедрение многопользовательского взаимодействия. Это потребует развертывания и администрирования серверной инфраструктуры. Процессы монтажа, настройки и длительной эксплуатации серверного оборудования сопряжены с воздействием на работников комплекса опасных и вредных производственных факторов. В данной главе проведен анализ условий труда системного администратора или разработчика, обслуживающего игровые серверы, и разработаны инженерно-технические мероприятия по обеспечению безопасности. Анализ выполнен на основе действующих нормативных документов.
Согласно ГОСТ 12.0.003-2015 [5], опасными производственными факторами называются факторы, воздействие которых на работника может привести к травме или другому внезапному резкому ухудшению здоровья, вплоть до летального исхода. Вредными производственными факторами считаются факторы, воздействие которых может вызвать заболевание или снижение трудоспособности. Все производственные факторы классифицируются по природе действия на четыре группы: физические, химические; биологические и психофизиологические.
Рабочее место специалиста, обслуживающего серверную инфраструктуру (серверная), характеризуется наличием физических и психофизиологических факторов, способных привести к травмам или профессиональным заболеваниям. В соответствии с классификацией по ГОСТ 12.0.003-2015 [5], для работников серверных помещений характерны факторы, представленные в таблице 4.1.

Таблица 4.1 – Опасные и вредные производственные факторы серверной

Повышенное значение напряжения в электрической цепи	Силовые кабели, блоки питания, распределительные щиты	Электротравмы (ожоги, фибрилляция, летальный исход)

Наиболее критичными, с точки зрения немедленного ущерба здоровью, являются опасность поражения электрическим током и пожарная опасность. При работе с серверным оборудованием специалист имеет дело с открытыми токоведущими частями. Опасность усугубляется наличием заземленных металлических конструкций и работой в ограниченном пространстве.
Также следует учитывать высокий уровень акустического шума, генерируемого десятками вентиляторов. Согласно СанПиН 2.2.4.3359-16 [21], предельно допустимый уровень (далее – ПДУ) шума на рабочих местах для трудовой деятельности, требующей концентрации, составляет 50 дБА. Фактические замеры вблизи работающей серверной стойки могут показывать значения 70–85 дБА. Это превышает установленный ПДУ шума более чем на 20 дБА, что классифицирует условия труда как вредные и требует применения средств защиты органов слуха и выноса рабочего места оператора в изолированное помещение.
Обеспечение пожарной и электробезопасности при развертывании игровых серверов
Помещение серверной, согласно СП 12.13130.2009 [23], относится к категории «В» (пожароопасное), так как в нем обращаются твердые горючие материалы (изоляция кабелей, пластиковые корпуса, текстолит плат). Основными причинами возгорания могут стать короткое замыкание, перегрузка силовых цепей и неисправность источников бесперебойного питания (аккумуляторных батарей).
Для предотвращения поражения электрическим током и возникновения пожаров необходимо строго соблюдать требования ПУЭ (Правила устройства электроустановок) [19] и Федерального закона № 123-ФЗ [33]. Все металлические нетоковедущие части оборудования, которые могут оказаться под напряжением вследствие пробоя изоляции, подлежат обязательному занулению. Схема защитного зануления представлена на рисунке 4.1.


Рис. 4.1 – Схема защитного зануления серверного оборудования

Электробезопасность обеспечивается следующими мерами.
Применение устройства защитного отключения (далее – УЗО) с током срабатывания не более 30 мА для розеточных групп.

Мероприятия по обеспечению безопасности при разработке и эксплуатации серверной инфраструктуры игрового проекта
На основе проведенного анализа условий труда и требований нормативных документов разработан комплекс организационно-технических и санитарно-гигиенических мероприятий, направленных на минимизацию рисков для здоровья персонала и повышение устойчивости работы игрового сервера.
Организационные мероприятия. К работе в серверной допускаются лица не моложе 18 лет, прошедшие медицинский осмотр и имеющие группу по электробезопасности не ниже III. Инструктаж на рабочем месте должен включать особенности тушения электроустановок под напряжением и действия при аварийной остановке игрового билда. Так как разработка и сопровождение серверной инфраструктуры для будущего мультиплеера предполагает длительное присутствие персонала, режим труда и отдыха должен соответствовать требованиям СанПиН 2.2.4.3359-16 [21]. Рекомендуются регламентированные перерывы на 15 минут каждые 2 часа для снижения статического напряжения и выхода из зоны шума.
При монтаже и ремонте серверных стоек необходимо использовать исправный электрифицированный инструмент с двойной изоляцией, а также диэлектрические коврики и перчатки. Все работы по ремонту блоков питания (даже тестовых сборок игрового сервера) проводятся только после отключения оборудования от сети и снятия статического электричества.
Технические мероприятия по нормализации микроклимата и шума. Для поддержания оптимальных параметров микроклимата (температура 20–22 °C, влажность 40–60 %) применяется прецизионная система кондиционирования с резервированием N+1. Для снижения шумового воздействия на разработчика, выполняющего отладку серверного кода прямо в машинном зале, рекомендуется применять строительные наушники с активным шумоподавлением или вынести рабочее место оператора (консоль KVM) в изолированное помещение – диспетчерскую.
Планировка серверного помещения должна обеспечивать свободный доступ для обслуживания. Ширина проходов между стойками должна быть не менее 1,0 м спереди и 0,8 м позади стоек. Обеспечение безопасности в аварийных режимах. При разработке сетевого кода игры следует реализовать корректную обработку исключений и ведение логов. С точки зрения охраны труда, это снижает нервно-психические перегрузки администратора при поиске причин краша билда. Оценка затрат на реализацию проекта
Оценка трудовых затрат рассчитывается исходя из оклада и времени работы сотрудника: заработная плата рассчитывается по формуле [22] ЗП=(Оклад/МФРВ)*tраб*Премия*Кур, где ФРВ – среднемесячный фонд рабочего времени; t раб – рабочее время, премия (15-30%) кур – уральский коэффициент, 15%. Помимо заработной платы необходимо учитывать также отчисления на соц. нужды – Отч=ЗП*0,304, которые включают в себя обязательное пенсионное страхование, обязательное медицинское страхование, на случаи временной нетрудоспособности и материнства, а также на травматизм. Помимо этого, необходимо учитывать прочие затраты, для их расчета необходимо воспользоваться формулой Прочие=ЗП*0,03.

В разделе выполнен анализ условий труда персонала, обслуживающего серверную инфраструктуру, необходимую для перспективного многопользовательского режима, при этом в ходе работы идентифицированы опасные и вредные производственные факторы и предложены мероприятия по электробезопасности. Итог: риски перечислены и «приземлены» на нормативные требования.
Организационные и санитарно‑гигиенические меры предусматривают вынос рабочего места оператора из шумной зоны, поддержание оптимального микроклимата (20–22 °C, влажность 40–60 %) и эргономичную планировку с холодным и горячим коридорами. Вывод короток: безопасность достигается сочетанием инженерных и административных решений.
Дополнительно выполнена комплексная оценка эффективности реализации проекта: STEP‑анализ подтверждает благоприятные условия на рынке инди‑игр, SWOT‑анализ фиксирует потенциал коммерциализации, расчёты показывают общие затраты 816 352 руб., срок окупаемости 6 месяцев, чистый дисконтированный доход 84 212 руб., что интерпретируется как экономическая целесообразность дальнейшего развития и коммерциализации. Итог: проект обоснован и с экономической, и с организационной позиции.
Заключение
В результате выполнения выпускной квалификационной работы достигнута поставленная цель, заключающаяся в разработке двухмерной ролевой игры с видом сверху и интеграции интеллектуальной системы поведения неигровых персонажей, обеспечивающей более осмысленное и устойчивое поведение союзников и противников в боевой ситуации, причём полученный программный продукт включает игровой фундамент, необходимый для проверки поведения NPC в условиях, приближенных к реальному игровому процессу (управление персонажем, оружие, способности, противники, инвентарь, экипировка, система группы, навигация, тренировочная среда для обучения модели). Итог: ИИ‑подсистема верифицирована в составе целостного приложения.
Первая глава, будучи посвящена анализу предметной области и современных подходов к игровому искусственному интеллекту и процедурной генерации, позволяет утверждать, что для 2D top-down roguelike RPG недостаточно ограничиваться простыми конечными автоматами либо полностью нейросетевым управлением: классические методы обеспечивают объяснимость и контролируемость, однако теряют гибкость при росте сложности, тогда как обучение с подкреплением способствует формированию адаптивных решений, но требует значительных ресурсов и усложняет отладку. Резюмируя, обоснован выбор гибридной архитектуры, объединяющей деревья поведения, Utility AI и обучаемый ML компонент.
Во второй главе обоснованы инструментальные средства и сформирована архитектура интеллектуальной системы NPC: в качестве платформы выбран Unity 6, поскольку он предоставляет компонентную модель, средства 2D‑разработки, навигацию, Unity Behavior и Unity ML-Agents; для союзников спроектирована гибридная архитектура, в которой Unity Behavior отвечает за организацию действий, Utility AI – за выбор цели и способности, ML-Agents – за боевое позиционирование, тогда как для массовых противников применён более простой и предсказуемый конечный автомат, соответствующий требованиям вычислительной экономичности и геймдизайнерской управляемости. Итоговый тезис: асимметричное распределение сложности обеспечивает баланс качества и производительности.
Третья глава включает практическую реализацию: разработаны базовые игровые механики и интеллектуальная система союзника, содержащая AllyAIBrain, CombatPerception, ThreatPerception, WeaponTargetSelector, UtilityAbilitySelector, AllyPositionAgent, AllyMLBridge и AllyMLMovementModifier; обучаемый агент AllyPosition использует 17 векторных наблюдений и 4 непрерывных действия, задающих параметры боевой дистанции, срочность отступления, направление и интенсивность стрейфа, причём модель выдаёт интерпретируемые параметры, исполняемые игровыми компонентами через NavMesh, что уменьшает риск некорректного поведения и сохраняет отладочность. Вывод краток: ML интегрирован как модуль позиционирования, а не как «сквозной» контроллер.
Для обучения создана сцена ML_Training_Arena с механизмами сброса эпизодов, генерацией волн, системой наград и учебной программой усложнения; в ходе экспериментов устранены дефекты, связанные со сбросом оружия, завершением эпизодов, структурой графа поведения и генерацией волн, после чего успешный прогон ally_headless_v1 доведён до 1 000 054 шагов и завершён экспортом ONNX‑модели. Экспериментальное сравнение эвристического и обученного режимов на 30 эпизодах максимальной сложности показывает увеличение успешности с 90 % до 100 %, рост средней награды с 4,01 до 5,49 и снижение стандартного отклонения с 5,34 до 1,28, что подтверждает повышение стабильности поведения союзника. Итог: обученная политика обеспечивает более предсказуемый результат.
Четвёртая глава охватывает безопасность и экономическую эффективность: выполнен анализ факторов при обслуживании серверной инфраструктуры и предложены меры по электробезопасности, пожарной безопасности, снижению шума и поддержанию микроклимата; экономический раздел фиксирует общие затраты 816 352 руб., срок окупаемости 6 месяцев и чистый дисконтированный доход 84 212 руб., что подтверждает целесообразность дальнейшего развития проекта. Резюмируя, поставленные во введении задачи выполнены, а разработанное решение демонстрирует практическую реализуемость гибридного подхода к управлению NPC в 2D roguelike RPG.
Перспективы развития темы связываются с расширением игровой и исследовательской составляющих: внедрение процедурной генерации уровней, соответствующей природе roguelike, способно повысить реиграбельность и одновременно расширить разнообразие тренировочных ситуаций для ML‑агента, улучшая обобщающую способность политики и снижая риск переобучения на фиксированную арену; модульность системы и интеграция через ScriptableObject‑профили упрощают дальнейшую настройку параметров без изменения кода, а экспорт модели в ONNX обеспечивает применение политики в режиме Inference непосредственно в игровом процессе. Итоговый вывод краток: предложенная архитектура масштабируется как по контенту, так и по сложности ИИ.

public class AllyAIBrain : MonoBehaviour
{
    public float AttackDistance
    {
        get
        {
            WeaponBase weapon = _activeWeapon != null ? _activeWeapon.GetActiveWeapon() : null;
            float baseRange = 1.5f;
            if (weapon != null && weapon.WeaponData != null)
                baseRange = CombatPerception.GetWeaponRange(weapon.WeaponData);
            float scale = _profileDistanceScale;
            if (_mlBridge != null)
                scale *= _mlBridge.GetCombatDistanceScale();
            return baseRange * scale;
        }
    }
    private void Awake()
    {
        if (_perception == null) _perception = GetComponent<CombatPerception>();
        if (_stats == null) _stats = GetComponent<PlayerStats>();
        if (_abilitySystem == null) _abilitySystem = GetComponent<AbilitySystem>();
        if (_activeWeapon == null) _activeWeapon = GetComponentInChildren<ActiveWeapon>(true);
        if (_mlBridge == null) _mlBridge = GetComponent<AllyMLBridge>();
        if (_profile == null) ApplyProfile(AllyAIProfile.CreateRuntimeDefault(_fallbackProfileType));
        else ApplyProfile(_profile);
    }
    private void OnDisable()
    {
        if (_currentWeaponTarget != null)
        {
            PartyCombatCoordinator.UnregisterFocus(_currentWeaponTarget);
            _currentWeaponTarget = null;
        }
    }
    private void FixedUpdate()
    {
        _snapshotTimer -= Time.fixedDeltaTime;
        if (_snapshotTimer <= 0f)
        {
            _snapshotTimer = _snapshotRefreshInterval;
            RefreshSnapshot();
        }
    }
    public void ApplyProfile(AllyAIProfile profile)
    {
        _profile = profile;
        if (_profile != null)
        {
            _profileLabel = _profile.ProfileType.ToString();
            _profileDistanceScale = _profile.PreferredCombatDistanceScale;
            if (_profile.WeaponTargetWeights != null)
                _weaponTargetWeights = _profile.WeaponTargetWeights;
            if (_profile.AbilityScoreWeights != null)
                _abilityScoreWeights = _profile.AbilityScoreWeights;
            _mlBridge?.ApplyProfileDefaults(_profile);
        }
        else
        {
            _profileLabel = "Default";
            _profileDistanceScale = 1f;
        }
        _abilitySelector = new UtilityAbilitySelector(_abilityScoreWeights);
    }
    public CombatSnapshot RefreshSnapshot()
    {
        if (_perception == null) return default;
        _cachedSnapshot = _perception.BuildSnapshot();
        return _cachedSnapshot;
    }
    public TargetSelectionResult SelectWeaponTarget(bool forceRefresh = false)
    {
        if (forceRefresh || _cachedSnapshot.Enemies == null) RefreshSnapshot();
        _lastWeaponTarget = WeaponTargetSelector.Select(_cachedSnapshot, _weaponTargetWeights);
        if (_currentWeaponTarget != _lastWeaponTarget.Target)
        {
            if (_currentWeaponTarget != null)
                PartyCombatCoordinator.UnregisterFocus(_currentWeaponTarget);
            _currentWeaponTarget = _lastWeaponTarget.Target;
            if (_currentWeaponTarget != null)
                PartyCombatCoordinator.RegisterFocus(_currentWeaponTarget);
        }
        return _lastWeaponTarget;
    }

        if (forceRefresh || _cachedSnapshot.Enemies == null)

        _lastAbilityDecision = _abilitySelector.Select(_cachedSnapshot, _abilitySystem, _activeWeapon);
        return _lastAbilityDecision;
    }
    public bool TryUseSelectedAbility()
    {

        if (data == null)
            return $"slot {slotIndex}";
        return string.IsNullOrWhiteSpace(data.DisplayName) ? data.AbilityType.ToString() : data.DisplayName;
    }

public class CombatPerception : MonoBehaviour
{
    private void Awake()
    {
        if (_stats == null)
            _stats = GetComponent<PlayerStats>();
        if (_activeWeapon == null)
            _activeWeapon = GetComponentInChildren<ActiveWeapon>(true);
        _self = _stats as ICharacterEntity;
        if (_self == null && _stats != null)
            _self = _stats;
    }
    public CombatSnapshot BuildSnapshot()
    {
        Vector3 position = transform.position;
        float healthPercent = 1f;
        float manaPercent = 1f;
        if (_stats != null)
        {
            healthPercent = _stats.MaxHealth > 0f ? _stats.Health / _stats.MaxHealth : 0f;
            manaPercent = _stats.MaxMana > 0f ? _stats.Mana / _stats.MaxMana : 0f;
        }
        WeaponType weaponType = WeaponType.Sword;
        float weaponRange = 1.5f;
        float optimalRange = 1f;
        WeaponBase weapon = _activeWeapon != null ? _activeWeapon.GetActiveWeapon() : null;
        if (weapon != null && weapon.WeaponData != null)
        {
            weaponType = weapon.WeaponData.WeaponType;
            weaponRange = GetWeaponRange(weapon.WeaponData);
            optimalRange = GetOptimalRange(weapon.WeaponData);
        }
        int enemyCount = GatherEnemies(position);
        int allyCount = GatherAllies(position);
        int clustered = CountClusteredEnemies(enemyCount);
        bool anyAllyLow = AnyAllyBelowThreshold(allyCount, _allyLowHealthThreshold);
        bool anyInCombat = AnyEnemyInCombat(enemyCount);
        float nearestDist = GetNearestEnemyDistance(enemyCount);
        CountAttackingEnemies(enemyCount, out int attackingEnemyCount, out int attackingSelfCount);
        LastSnapshot = new CombatSnapshot
        {
            Position = position,
            HealthPercent = healthPercent,
            ManaPercent = manaPercent,
            EquippedWeapon = weaponType,
            WeaponRange = weaponRange,
            OptimalWeaponRange = optimalRange,
            Enemies = CopyEnemySlice(enemyCount),
            Allies = CopyAllySlice(allyCount),
            EnemyCount = enemyCount,
            ClusteredEnemyCount = clustered,
            AnyAllyLowHealth = anyAllyLow,
            NearestEnemyDistance = nearestDist,
            AnyEnemyInCombat = anyInCombat,
            AttackingEnemyCount = attackingEnemyCount,
            AttackingSelfCount = attackingSelfCount
        };
        return LastSnapshot;
    }
    private int GatherEnemies(Vector3 origin)
    {
        int count = EnemyPhysics2D.OverlapCircle(origin, _scanRadius, _enemyBuffer);
        int written = 0;
        for (int i = 0; i < count && written < _enemySnapshots.Length; i++)
        {
            Collider2D c = _enemyBuffer[i];
            if (c == null) continue;
            if (!c.TryGetComponent(out EnemyDamage ed) || !ed.IsAlive) continue;
            float dist = Vector2.Distance(origin, c.transform.position);
            bool isAttacking = false;
            bool isAttackingSelf = false;
            if (c.TryGetComponent(out EnemyAI ai))
            {
                isAttacking = ai.IsAttacking;
                isAttackingSelf = ai.IsAttackingEntity(_self);
            }
            _enemySnapshots[written++] = new EnemySnapshot
            {
                Transform = c.transform,
                Damage = ed,
                Distance = dist,
                HealthPercent = ed.HealthPercent,
                InCombat = ed.InCombat,
                FocusFireCount = PartyCombatCoordinator.GetFocusCount(c.transform),
                IsAttacking = isAttacking,
                IsAttackingSelf = isAttackingSelf
            };
        }
        return written;
    }
    private void CountAttackingEnemies(int enemyCount, out int attackingEnemyCount, out int attackingSelfCount)
    {
        attackingEnemyCount = 0;
        attackingSelfCount = 0;
        for (int i = 0; i < enemyCount; i++)
        {
            if (!_enemySnapshots[i].IsAttacking)
                continue;
            attackingEnemyCount++;
            if (_enemySnapshots[i].IsAttackingSelf)
                attackingSelfCount++;
        }
    }

    private int GatherAllies(Vector3 origin)
    {
        int written = 0;

        if (PartyManager.Instance == null)
            return 0;

        foreach (ICharacterEntity member in PartyManager.Instance.Members)
        {
            if (written >= _allySnapshots.Length) break;
            if (member == null || !member.IsAlive) continue;
            float maxHealth = member.StatSystem.GetFinalValue(StatType.HealthFlat);
            float health = maxHealth;
            if (member is PlayerStats ps)
                health = ps.Health;
            float healthPercent = maxHealth > 0f ? health / maxHealth : 1f;
            float dist = Vector2.Distance(origin, member.Transform.position);
            _allySnapshots[written++] = new AllySnapshot
            {
                Transform = member.Transform,
                Entity = member,
                Distance = dist,
                HealthPercent = healthPercent,
                IsSelf = member.Transform == transform
            };
        }
        return written;
    }
    private int CountClusteredEnemies(int enemyCount)
    {
        if (enemyCount <= 1)
            return enemyCount;
        int bestCluster = 0;
        for (int i = 0; i < enemyCount; i++)
        {
            Vector2 center = _enemySnapshots[i].Transform.position;
            int cluster = 0;
            for (int j = 0; j < enemyCount; j++)
            {
                if (Vector2.Distance(center, _enemySnapshots[j].Transform.position) <= _clusterRadius)
                    cluster++;
            }
            if (cluster > bestCluster)
                bestCluster = cluster;
        }
        return bestCluster;
    }
    private bool AnyAllyBelowThreshold(int allyCount, float threshold)
    {
        for (int i = 0; i < allyCount; i++)
        {
            if (_allySnapshots[i].IsSelf) continue;
            if (_allySnapshots[i].HealthPercent < threshold)
                return true;
        }
        return false;
    }
    private bool AnyEnemyInCombat(int enemyCount)
    {
        for (int i = 0; i < enemyCount; i++)
        {
            if (_enemySnapshots[i].InCombat)
                return true;
        }
        return false;
    }
    private float GetNearestEnemyDistance(int enemyCount)
    {
        float nearest = float.MaxValue;
        for (int i = 0; i < enemyCount; i++)
            nearest = Mathf.Min(nearest, _enemySnapshots[i].Distance);
        return nearest == float.MaxValue ? -1f : nearest;
    }
    private EnemySnapshot[] CopyEnemySlice(int count)
    {
        var slice = new EnemySnapshot[count];
        for (int i = 0; i < count; i++)
            slice[i] = _enemySnapshots[i];
        return slice;
    }
    private AllySnapshot[] CopyAllySlice(int count)
    {
        var slice = new AllySnapshot[count];
        for (int i = 0; i < count; i++)
            slice[i] = _allySnapshots[i];
        return slice;
    }
    public static float GetWeaponRange(WeaponSO data)
    {
        if (data == null)
            return 1.5f;
        return data.ResolveMaxCombatRange();
    }
    public static float GetOptimalRange(WeaponSO data)
    {
        if (data == null)
            return 1.2f;
        return data.ResolveOptimalCombatRange();
    }
}

public class ThreatPerception : MonoBehaviour
{
    private void Awake()
    {
        if (_combatPerception == null)
            _combatPerception = GetComponent<CombatPerception>();
    }
    public ThreatSnapshot BuildSnapshot(Vector3 position, CombatSnapshot combat)
    {
        _threatBuffer.Clear();
        ThreatSnapshot snapshot = default;
        snapshot.AttackingEnemyCount = combat.AttackingEnemyCount;
        snapshot.AttackingSelfCount = combat.AttackingSelfCount;
        snapshot.AnyEnemyAttackingSelf = combat.AttackingSelfCount > 0;
        snapshot.NearestEnemyAttacking = combat.AttackingEnemyCount > 0;
        snapshot.NearestEnemyBearing = GetNearestAttackingSelfBearing(position, combat);
        EvaluateAttackingEnemies(position, combat, ref snapshot);
        EvaluateIncomingProjectiles(position);
        ApplyAggregatedThreat(ref snapshot);
        LastSnapshot = snapshot;
        return snapshot;
    }
    private static float GetNearestAttackingSelfBearing(Vector3 position, CombatSnapshot combat)
    {
        if (combat.Enemies == null || combat.EnemyCount == 0)
            return 0.5f;
        float nearest = float.MaxValue;
        Vector2 toEnemy = Vector2.right;
        for (int i = 0; i < combat.EnemyCount; i++)
        {
            EnemySnapshot enemy = combat.Enemies[i];
            if (enemy.Transform == null || !enemy.IsAttackingSelf || enemy.Distance >= nearest)
                continue;
            nearest = enemy.Distance;
            toEnemy = (Vector2)(enemy.Transform.position - position);
        }
        if (nearest == float.MaxValue)
            return GetNearestEnemyBearing(position, combat);
        if (toEnemy.sqrMagnitude < 0.0001f)
            return 0.5f;
        float angle = Mathf.Atan2(toEnemy.y, toEnemy.x);
        return Mathf.Repeat(angle / (Mathf.PI * 2f) + 0.5f, 1f);
    }
    private static float GetNearestEnemyBearing(Vector3 position, CombatSnapshot combat)
    {
        float nearest = float.MaxValue;
        Vector2 toEnemy = Vector2.right;
        for (int i = 0; i < combat.EnemyCount; i++)
        {
            EnemySnapshot enemy = combat.Enemies[i];
            if (enemy.Transform == null || enemy.Distance >= nearest)
                continue;
            nearest = enemy.Distance;
            toEnemy = (Vector2)(enemy.Transform.position - position);
        }
        if (nearest == float.MaxValue || toEnemy.sqrMagnitude < 0.0001f)
            return 0.5f;
        float angle = Mathf.Atan2(toEnemy.y, toEnemy.x);
        return Mathf.Repeat(angle / (Mathf.PI * 2f) + 0.5f, 1f);
    }
    private void EvaluateAttackingEnemies(Vector3 position, CombatSnapshot combat, ref ThreatSnapshot snapshot)
    {
        if (combat.Enemies == null)
            return;
        Vector2 allyPos = position;
        float maxSelfUrgency = 0f;
        for (int i = 0; i < combat.EnemyCount; i++)
        {
            EnemySnapshot enemy = combat.Enemies[i];
            if (enemy.Transform == null || !enemy.IsAttacking)
                continue;
            if (enemy.Distance > _meleeThreatRadius)
                continue;
            Vector2 awayFromAttacker = allyPos - (Vector2)enemy.Transform.position;
            if (awayFromAttacker.sqrMagnitude < 0.0001f)
                awayFromAttacker = Vector2.right;
            awayFromAttacker.Normalize();
            float proximity = 1f - Mathf.Clamp01(enemy.Distance / _meleeThreatRadius);
            float urgency = enemy.IsAttackingSelf
                ? 0.65f + proximity * 0.35f
                : 0.35f + proximity * 0.25f;
            if (enemy.IsAttackingSelf)
                maxSelfUrgency = Mathf.Max(maxSelfUrgency, urgency);
            AddThreat(awayFromAttacker, urgency, enemy.Distance, 0f);
        }
        snapshot.AttackingSelfUrgency = maxSelfUrgency;
    }
    private void EvaluateIncomingProjectiles(Vector3 position)
    {
        IReadOnlyList<Projectile> projectiles = EnemyProjectileRegistry.ActiveProjectiles;
        Vector2 allyPos = position;
        for (int i = 0; i < projectiles.Count; i++)
        {
            Projectile projectile = projectiles[i];
            if (projectile == null || !projectile.EnemyLaunch)
                continue;
            Rigidbody2D rb = projectile.GetComponent<Rigidbody2D>();
            if (rb == null)
                continue;
            Vector2 projectilePos = projectile.transform.position;
            float distance = Vector2.Distance(allyPos, projectilePos);
            if (distance > _threatScanRadius)
                continue;
            Vector2 velocity = rb.linearVelocity;
            float speed = velocity.magnitude;
            if (speed < 0.01f)
                continue;
            Vector2 toAlly = allyPos - projectilePos;
            if (toAlly.sqrMagnitude < 0.0001f)
                continue;
            Vector2 moveDir = velocity / speed;
            float alignment = Vector2.Dot(moveDir, toAlly.normalized);
            if (alignment < _threatAlignmentThreshold)
                continue;
            float timeToImpact = distance / speed;
            if (timeToImpact > _maxThreatTime)
                continue;
            float urgency = Mathf.Clamp01(1f - timeToImpact / _maxThreatTime);
            Vector2 lateral = new Vector2(-moveDir.y, moveDir.x);
            if (Vector2.Dot(lateral, toAlly) < 0f)
                lateral = -lateral;
            AddThreat(lateral, urgency, distance, timeToImpact);
        }
    }
    private void AddThreat(Vector2 escapeDirection, float urgency, float distance, float timeToImpact)
    {
        if (escapeDirection.sqrMagnitude < 0.0001f || urgency <= 0f)
            return;
        _threatBuffer.Add(new ThreatEntry
        {
            EscapeDirection = escapeDirection.normalized,
            Urgency = urgency,
            Distance = distance,
            TimeToImpact = timeToImpact
        });
    }
    private void ApplyAggregatedThreat(ref ThreatSnapshot snapshot)
    {
        _threatBuffer.Sort((a, b) => b.Urgency.CompareTo(a.Urgency));
        int count = Mathf.Min(_threatBuffer.Count, _maxThreatEntries);
        Vector2 weightedEscape = Vector2.zero;
        float bestUrgency = 0f;
        float bestDistance = float.MaxValue;
        float bestTime = float.MaxValue;
        for (int i = 0; i < count; i++)
        {
            ThreatEntry entry = _threatBuffer[i];
            weightedEscape += entry.EscapeDirection * entry.Urgency;
            bestUrgency = Mathf.Max(bestUrgency, entry.Urgency);
            bestDistance = Mathf.Min(bestDistance, entry.Distance);
            if (entry.TimeToImpact > 0f)
                bestTime = Mathf.Min(bestTime, entry.TimeToImpact);
        }
        _threatBuffer.Clear();
        float meleeUrgency = snapshot.AttackingSelfUrgency;
        if (meleeUrgency > bestUrgency)
            bestUrgency = meleeUrgency;
        snapshot.HasIncomingThreat = bestUrgency > 0f;
        snapshot.IncomingThreatUrgency = bestUrgency;
        snapshot.NearestThreatDistance = bestDistance == float.MaxValue ? -1f : bestDistance;
        snapshot.NearestThreatTimeToImpact = bestTime == float.MaxValue ? -1f : bestTime;
        snapshot.ThreatDirection = weightedEscape.sqrMagnitude > 0.0001f
            ? weightedEscape.normalized
            : Vector2.zero;
    }
}

public class AllyMLMovementModifier : MonoBehaviour
{
    private void Awake()
    {
        if (_brain == null) _brain = GetComponent<AllyAIBrain>();
        if (_mlBridge == null) _mlBridge = GetComponent<AllyMLBridge>();
        if (_threatPerception == null) _threatPerception = GetComponent<ThreatPerception>();
        if (_dodgeHeuristic == null) _dodgeHeuristic = GetComponent<AllyDodgeHeuristic>();
        EnsureComponent(ref _threatPerception);
        EnsureComponent(ref _dodgeHeuristic);
        _navMeshAgent = GetComponentInChildren<NavMeshAgent>();
    }
    private void EnsureComponent<T>(ref T component) where T : Component
    {
        if (component != null) return;
        component = GetComponent<T>();
        if (component == null) component = gameObject.AddComponent<T>();
    }
    private void FixedUpdate()
    {
        if (!ShouldControlMovement())
        {
            IsControllingMovement = false;
            return;
        }
        IsControllingMovement = true;
        _refreshTimer -= Time.fixedDeltaTime;
        if (_refreshTimer > 0f) return;
        _refreshTimer = _destinationRefreshInterval;
        ApplyCombatDestination();
    }
    public void SetGraphDriving(bool active)
    {
        _graphDriving = active;
        if (!active)
        {
            IsControllingMovement = false;
            _isInLowHealthEscape = false;
        }
    }
    public void SetMovementContext(
        float healthPercent,
        float lowHealthThreshold,
        float maxDistToLeader,
        float lowHealthHysteresis = -1f)
    {
        _healthPercent = healthPercent;
        _lowHealthThreshold = lowHealthThreshold;
        _maxDistToLeader = maxDistToLeader;
        if (lowHealthHysteresis >= 0f) _lowHealthHysteresis = lowHealthHysteresis;
    }
    public bool ShouldControlMovement()
    {
        if (_mlBridge == null || _brain == null) return false;
        if (!_mlBridge.IsMLActive || !_mlBridge.UseMLCombatMovement) return false;
        if (_graphDriving)
        {
            return EvaluateMovementMode() switch
            {
                AllyMLMovementMode.EscapeToAlly => true,
                AllyMLMovementMode.FollowLeader => GetLeaderDistance() > _maxDistToLeader,
                _ => HasCombatMovementTarget()
            };
        }
        return HasCombatMovementTarget();
    }
    public Vector3 ComputeDesiredWorldPosition()
    {
        CombatSnapshot combat = _brain.Snapshot;
        ThreatSnapshot threat = _threatPerception != null
            ? _threatPerception.BuildSnapshot(transform.position, combat) : default;
        CurrentMode = EvaluateMovementMode();
        Vector2 desired = CurrentMode switch
        {
            AllyMLMovementMode.EscapeToAlly => ComputeEscapePosition(combat),
            AllyMLMovementMode.FollowLeader => ComputeFollowLeaderPosition(),
            _ => ComputeCombatPosition(combat)
        };
        desired = ApplyThreatMitigation(desired, threat);
        return new Vector3(desired.x, desired.y, transform.position.z);
    }
    private AllyMLMovementMode EvaluateMovementMode()
    {
        UpdateLowHealthEscapeState();
        if (_isInLowHealthEscape) return AllyMLMovementMode.EscapeToAlly;
        if (GetLeaderDistance() > _maxDistToLeader) return AllyMLMovementMode.FollowLeader;
        if (HasCombatMovementTarget())return AllyMLMovementMode.CombatPositioning;
        return AllyMLMovementMode.FollowLeader;
    }
    private void UpdateLowHealthEscapeState()
    {
        if (!HasCombatMovementTarget())
        {
            _isInLowHealthEscape = false;
            return;
        }
        float exitThreshold = _lowHealthThreshold + _lowHealthHysteresis;
        if (!_isInLowHealthEscape && _healthPercent <= _lowHealthThreshold)
            _isInLowHealthEscape = true;
        if (_isInLowHealthEscape && _healthPercent >= exitThreshold)
            _isInLowHealthEscape = false;
    }
    private bool HasCombatMovementTarget()
    {
        CombatSnapshot snapshot = _brain.Snapshot;
        return snapshot.EnemyCount > 0 && _brain.CurrentWeaponTarget != null;
    }
    private Vector2 ComputeCombatPosition(CombatSnapshot combat)
    {
        Transform target = _brain.CurrentWeaponTarget;
        if (target == null) return transform.position;
        Vector2 allyPos = transform.position;
        Vector2 enemyPos = target.position;
        Vector2 toEnemy = enemyPos - allyPos;
        float currentDist = toEnemy.magnitude;
        if (currentDist < 0.01f) toEnemy = Vector2.right;
        else toEnemy /= currentDist;
        float targetDist = Mathf.Max(_brain.AttackDistance, 0.5f);
        Vector2 ringPoint = enemyPos - toEnemy * targetDist;
        Vector2 perp = new Vector2(-toEnemy.y, toEnemy.x);
        float strafeDir = _mlBridge.GetStrafeDirectionSigned();
        float strafeIntensity = _mlBridge.StrafeIntensity;
        Vector2 strafeOffset = perp * (strafeDir * strafeIntensity * _strafeRadius);
        Vector2 desired = ringPoint + strafeOffset;
        float distError = currentDist - targetDist;
        if (distError < -_distanceTolerance)
        {
            float retreatBlend = Mathf.Clamp01(_mlBridge.RetreatUrgency + 0.25f);
            desired = allyPos - toEnemy * (_destinationStep * retreatBlend);
        }
        else if (distError > _distanceTolerance)
 desired = Vector2.Lerp(allyPos, ringPoint, 0.65f);
        if (_mlBridge.ShouldForceRetreat) desired = allyPos - toEnemy * _destinationStep;
        return desired;
    }
    private Vector2 ComputeEscapePosition(CombatSnapshot combat)
    {
        Vector2 allyPos = transform.position;
        if (!TryGetPartyAnchor(allyPos, out Vector2 anchor, out float distToAnchor))
            return ComputeFallbackEscape(allyPos);
        if (distToAnchor > _maxEscapeDistanceFromParty)
            return MoveToward(allyPos, anchor, _escapeApproachStep * 1.25f);
        Transform enemy = _brain.CurrentWeaponTarget;
        float enemyDist = enemy != null
            ? Vector2.Distance(allyPos, enemy.position)
            : float.MaxValue;
        if (distToAnchor > _allyHoldRadius)
        {
            Vector2 holdPoint = GetHoldPointNearAnchor(anchor, enemy, allyPos);
            float step = Mathf.Lerp(_escapeApproachStep, _escapeApproachStep * 0.5f,
                1f - Mathf.Clamp01(distToAnchor / _maxEscapeDistanceFromParty));
            return MoveToward(allyPos, holdPoint, step);
        }
        if (enemy != null && enemyDist < _enemyThreatRadiusDuringEscape)
        {
            Vector2 awayFromEnemy = allyPos - (Vector2)enemy.position;
            if (awayFromEnemy.sqrMagnitude < 0.0001f) awayFromEnemy = Vector2.right;
            awayFromEnemy.Normalize();
            float threatBlend = Mathf.InverseLerp(_allyHoldRadius, 0f, enemyDist);
            return allyPos + awayFromEnemy * (_holdRetreatStep * threatBlend);
        }
        Vector2 settlePoint = GetHoldPointNearAnchor(anchor, enemy, allyPos);
        if (Vector2.Distance(allyPos, settlePoint) > 0.35f)
            return MoveToward(allyPos, settlePoint, _holdRetreatStep * 0.5f);
        return allyPos;
    }
    private Vector2 ComputeFallbackEscape(Vector2 allyPos)
    {
        Transform enemy = _brain.CurrentWeaponTarget;
        if (enemy == null)
            return ComputeFollowLeaderPosition();
        Vector2 awayFromEnemy = allyPos - (Vector2)enemy.position;
        if (awayFromEnemy.sqrMagnitude < 0.0001f) awayFromEnemy = Vector2.right;
        return allyPos + awayFromEnemy.normalized * _holdRetreatStep;
    }
    private Vector2 GetHoldPointNearAnchor(Vector2 anchor, Transform enemy, Vector2 allyPos)
    {
        if (enemy == null) return anchor;
        Vector2 awayFromEnemy = anchor - (Vector2)enemy.position;
        if (awayFromEnemy.sqrMagnitude < 0.0001f) return anchor;
        awayFromEnemy.Normalize();
        float offset = _allyHoldRadius * 0.45f;
        Vector2 holdPoint = anchor + awayFromEnemy * offset;
        float distToHold = Vector2.Distance(allyPos, holdPoint);
        if (distToHold > _allyHoldRadius) holdPoint = Vector2.Lerp(anchor, holdPoint, _allyHoldRadius / distToHold);
        return holdPoint;
    }
    private static Vector2 MoveToward(Vector2 from, Vector2 to, float step)
    {
        return Vector2.MoveTowards(from, to, step);
    }
    private Vector2 ComputeFollowLeaderPosition()
    {
        Vector2 allyPos = transform.position;
        Transform leader = PartyManager.Instance?.LeaderTransform;
        if (leader == null) return allyPos;
        Vector2 leaderPos = leader.position;
        float dist = Vector2.Distance(allyPos, leaderPos);
        if (dist <= _maxDistToLeader * 0.85f) return allyPos;
        Vector2 toLeader = leaderPos - allyPos;
        if (toLeader.sqrMagnitude < 0.0001f) return allyPos;
        toLeader.Normalize();
        float catchUp = Mathf.InverseLerp(_maxDistToLeader, _maxDistToLeader * 1.75f, dist);
        return allyPos + toLeader * (_followLeaderStep * Mathf.Clamp(catchUp, 0.35f, 1.25f));
    }
    private bool TryGetPartyAnchor(Vector2 allyPos, out Vector2 anchor, out float distToAnchor)
    {
        anchor = allyPos;
        distToAnchor = 0f;
        Transform leader = PartyManager.Instance?.LeaderTransform;
        if (leader != null)
        {
            anchor = leader.position;
            distToAnchor = Vector2.Distance(allyPos, anchor);
            return true;
        }
        if (PartyManager.Instance == null)
            return false;
        ICharacterEntity nearest = null;
        float minDistSq = float.MaxValue;
        foreach (ICharacterEntity member in PartyManager.Instance.Members)
        {
            if (member == null || !member.IsAlive)
                continue;
            if (member.Transform == transform)
                continue;
            float sq = ((Vector2)member.Transform.position - allyPos).sqrMagnitude;
            if (sq < minDistSq)
            {
                minDistSq = sq;
                nearest = member;
            }
        }
        if (nearest == null)
            return false;
        anchor = nearest.Transform.position;
        distToAnchor = Mathf.Sqrt(minDistSq);
        return true;
    }
    private Vector2 ApplyThreatMitigation(Vector2 desired, ThreatSnapshot threat)
    {
        if (_dodgeHeuristic == null)
            return desired;
        Vector2 dodge = _dodgeHeuristic.ComputeDodgeOffset(transform.position, threat);
        if (CurrentMode == AllyMLMovementMode.CombatPositioning && _mlBridge.StrafeIntensity > 0.05f)
            dodge *= 0.85f;
        return desired + dodge;
    }
    private float GetLeaderDistance()
    {
        Transform leader = PartyManager.Instance?.LeaderTransform;
        if (leader == null)
            return 0f;
        return Vector2.Distance(transform.position, leader.position);
    }
    private void ApplyCombatDestination()
    {
        if (_navMeshAgent == null || !_navMeshAgent.isOnNavMesh)
            return;
        Vector3 desired = ComputeDesiredWorldPosition();
        if (!TrySampleNavMesh(desired, out Vector3 valid))
            return;
        if (Vector3.Distance(valid, _lastDestination) < 0.05f)
            return;
        _lastDestination = valid;
        _navMeshAgent.isStopped = false;
        _navMeshAgent.SetDestination(valid);
    }
    private bool TrySampleNavMesh(Vector3 point, out Vector3 valid)
    {
        valid = point;
        if (!NavMesh.SamplePosition(point, out NavMeshHit hit, _navSampleRadius, NavMesh.AllAreas))
            return false;
        valid = hit.position;
        return true;
    }

    public override void Heuristic(in ActionBuffers actionsOut)

        CombatSnapshot snapshot = _brain != null ? _brain.Snapshot : default;
        ThreatSnapshot threat = _threatPerception != null
            ? _threatPerception.LastSnapshot
            : default;
        float preferred = snapshot.EnemyCount > 0 ? 0.55f : 0.35f;
        float retreat = 0f;
        float strafeDir = 0.5f;
        float strafeIntensity = 0f;
        if (_brain != null)
        {
            float shieldPct = GetShieldPercent();
            if (_brain.HealthPercent < 0.25f && shieldPct < 0.1f)
                retreat = 0.9f;

                retreat = 0.6f;
        }
        if (threat.HasIncomingThreat || threat.AnyEnemyAttackingSelf)
        {
            strafeIntensity = Mathf.Clamp01(Mathf.Max(threat.IncomingThreatUrgency, threat.AttackingSelfUrgency));
            if (threat.ThreatDirection.sqrMagnitude > 0.0001f)
            {
                Vector2 lateral = new Vector2(-threat.ThreatDirection.y, threat.ThreatDirection.x);
                strafeDir = lateral.x >= 0f ? 0.75f : 0.25f;

        {
            strafeIntensity = 0.35f;
            strafeDir = Mathf.PingPong(Time.time * 0.5f, 1f);

        continuous[2] = strafeDir;

            ? _threatPerception.LastSnapshot

            AddReward(_distanceRewardScale * (1f - Mathf.Clamp01(delta)));

        else if (PartyManager.Instance?.LeaderTransform != null)

                AddReward(-_followLeaderPenaltyScale * (dist - _maxLeaderFollowDistance));
        }
        if ((threat.AnyEnemyAttackingSelf || threat.AttackingEnemyCount > 0) && !_tookDamageThisStep)
            AddReward(_evadeWhileAttackingReward * (1f + threat.AttackingSelfUrgency));

            && threat.NearestThreatDistance <= _nearMissDistance)

            AddReward(_nearMissReward * threat.IncomingThreatUrgency);
